## Research Question

Can the current Universo implementation support one template-aware widget and layout contract across the Dashboard and marketing-page templates, while allowing a Page or Object entity to select a template different from the metahub/application default, without a schema, snapshot, or metahub-template version increase?

This research also checks whether the current brief is traceable to the original task, whether the earlier MUI and marketing-page research remains current, and which runtime, persistence, publication, synchronization, UX, accessibility, and test constraints must be closed before PLAN.

## Key Findings

### 1. The current brief is directionally correct, but the implementation baseline is more advanced than the brief's historical diagnosis

The original input correctly identifies the product problem: Dashboard and marketing-page layouts expose different widget sets and placement names, and a Page or Object should be able to choose a different layout template from the metahub/application default. It also correctly preserves the clean-break constraints: disposable test data, no legacy compatibility code, no schema or metahub-template version bump, and freedom to refactor.

The current checkout already has a typed registry in packages/universo-react-types/src/common/layoutWidgetDefinitions.ts:6-75, separate Dashboard and marketing definitions in metahubs.ts:833-874 and marketingPage.ts:14-139, a marketing-specific renderer, persisted marketing widget instances, seed validation, snapshot/materialization handling, and marketing lifecycle browser flows. The current marketing seed contains nine active instances: navigation, hero, five collection variants, pricing, and footer. Current documentation describes those instances as repeatable and the authoring tests exercise duplication, configuration, activation/deactivation, deletion, and reorder.

Therefore, the new work is not a second basic marketing-widgetization project. It is primarily a contract and resolution project:

-   define which metadata is template-neutral and which remains template-specific;
-   resolve the effective layout and template before selecting a renderer;
-   support cross-template entity-scoped selection and all required lifecycle paths;
-   remove runtime paths that omit or silently reinterpret persisted placements;
-   preserve the existing marketing lifecycle evidence while adding the missing cross-template evidence.

### 2. The registry is a good extension point, but it is not yet a neutral widget capability contract

layoutWidgetDefinitions.ts:6-75 currently combines dashboard and marketing definitions and records templateKey, zones, labels, and repeatability. marketingPage.ts:14-139 keeps marketing widget keys and config semantics separate from dashboard widgets. This is a sound boundary for keeping template renderers independent.

The registry is still partitioned by template. applicationTemplates.ts:15-29 explicitly marks Dashboard as supporting dashboard widgets and marketing-page as not supporting them. A dashboard languageSwitcher is therefore not automatically a widget that can be mounted in a marketing shell. The brief should not be implemented by adding every widget key to one union or by routing both templates through the dashboard renderWidget switch.

The safer contract is a neutral capability manifest plus template adapters:

-   the neutral part describes identity, lifecycle, placement intent, required host capabilities, configuration schema identity, data-binding roles, and accessibility expectations;
-   the selected template adapter validates its allowed physical placement and translates logical placement to its renderer;
-   each template retains its own renderer and shell semantics;
-   a widget is shared only when its capability requirements are actually provided by both hosts.

For example, languageSwitcher can become shared if both templates expose the same locale state, action, and accessible labeling contract. It must remain dashboard-only if marketing does not provide those capabilities. Shared metadata must not imply shared visual composition or shared data access.

### 3. Physical placement vocabularies differ and the runtime transport currently loses dashboard zones

The Dashboard registry defines left, top, right, bottom, and center. Marketing uses marketing-header, marketing-main, and marketing-footer. The current distinction is valid at the storage and renderer boundary, but it must be represented as an explicit mapping rather than an accidental union.

The strongest concrete defect is in packages/universo-react-applications-backend/src/controllers/runtimeRowsController.ts:5063-5131. Its runtime row query restricts zones to left, right, and center. Persisted Dashboard widgets in top or bottom are omitted from that response. The mapping has no independent rejection branch for an invalid fetched zone; with the current SQL predicate, an unknown persisted zone is filtered before that loop rather than safely surfaced. The controller also catches widget loading failures, logs a warning, and continues with an empty result. Thus the current runtime silently loses valid persisted zones and fails open on loading errors, which contradicts the brief's fail-closed goal.

By contrast, syncHelpers.ts and syncLayoutPersistence.ts contain stricter zone normalization that throws for an invalid template-zone combination. The research and eventual plan must distinguish these paths: authoring/sync validation is mostly fail-closed, while one runtime read path is not. The target contract should reject unknown logical or physical placements and surface a typed runtime failure rather than omit or reclassify them.

The frontend transport has the same gap. packages/universo-react-apps-template-mui/src/api/api.ts:137-139 and dashboard/Dashboard.tsx:165-169 currently describe only left, right, and center. A backend-only repair would still lose top/bottom at schema parsing, adapter, or render time. PLAN must decide the fate of every registered Dashboard zone across SQL selection, API schemas, frontend adapters, Dashboard rendering, and tests; no layer may silently drop or remap a persisted zone.

MUI's current guidance supports a semantic-region abstraction, not a promise that every template has identical CSS zones. MUI describes templates as distinct examples with reusable sections, recommends Stack for one-dimensional composition, and treats Grid as a two-dimensional layout system. The application contract should therefore use logical regions such as header, main, footer, sidebar, and auxiliary where useful, with an explicit per-template mapping to physical zones. It must not force a marketing page into dashboard left/top/right/bottom geometry.

### 4. Runtime template selection happens too early for entity-scoped cross-template layouts

Both hosted packages/universo-react-applications-frontend/src/pages/ApplicationRuntime.tsx:1007-1060 and standalone packages/universo-react-apps-template-mui/src/standalone/DashboardApp.tsx:882-917 first query /runtime/template and branch on the global templateKey. Only after that branch can the marketing-page path request the entity-targeted marketing read model. packages/universo-react-apps-template-mui/src/api/api.ts:166-174,250-275 currently models the bootstrap as templateKey and config, while packages/universo-react-applications-backend/src/controllers/runtimeMarketingPageController.ts:340-417 performs the later target-specific marketing selection. Its current target lookup filters \_app_objects to kind = object, so an existing Page target is not evidence-covered by this controller; Page and Object must enter the same target-aware resolver/API policy before renderer dispatch.

The marketing controller can select a scoped application layout for a target and falls back to the global application layout, but it rejects the selected layout when its template is not marketing-page. That is sufficient for same-template marketing overlays; it does not support the requested case where the global default is Dashboard and a Page/Object scoped layout is marketing-page.

The application authoring UI has the same limitation: ApplicationLayouts.tsx:562-603 derives applicationTemplateKey from the global default or first layout, then creates new layouts with that key even for an entity scope. The metahub service rejects a scoped layout template that differs from its global base template in MetahubLayoutsService.ts:542-588 and :1608-1700. These checks are coherent for the old same-template overlay model, but they directly prevent the new requirement.

Hosted and standalone runtime paths currently cache the template bootstrap for about 60 seconds. A target change must not reuse a global template/layout response simply because applicationId is unchanged. Every changing request input — effective target, scope kind, entity identifiers, record-selection context, locale/workspace/theme where response-dependent, and selected layout/template when already known — must be represented in the query key and response identity. The effective hash is a response freshness/version token, not a value to fabricate before the first request; it must drive targeted invalidation or an explicit follow-up version key. Layout/widget mutations must invalidate the targeted runtime and authoring prefixes and await invalidation before a success state is shown.

The implementation needs one server-owned effective-layout resolver that accepts the runtime target and returns at least:

-   target identity and scope kind;
-   selected layout identity;
-   selected template key;
-   source and base lineage;
-   precedence decisions;
-   resolved widget envelope and content/read-model contract;
-   a stable effective-layout hash;
-   a typed fail-closed reason when selection is invalid or ambiguous.

Renderer dispatch must consume that result. A client-side sequence that first commits to the global template and then tries to load an entity-specific template cannot satisfy the requirement reliably.

### 5. Same-template inheritance is implemented, but cross-template inheritance is not defined

syncHelpers.ts:903-1067, in materializeSnapshotLayoutsAndWidgets(), normalizes global layouts and applies scoped overlays. It throws when a scoped template differs from its base template, validates inherited widgets, preserves marketing instance keys, and builds a materialized scoped layout. However, it silently skips a scoped row when its base layout or scope row is missing. This is dangerous for a new contract where template choice itself can differ: a missing base must not become an unexplained omission.

The new brief must choose one of two explicit models:

1. A selected entity layout is self-contained when its template differs from the global default. It has its own valid widget composition and is not an incompatible overlay of the Dashboard base.
2. A cross-template projection is allowed, but the projection has an explicit compatibility map, source lineage, and rejection rules for every widget that cannot be projected.

The recommended default is the first model. Same-template sparse overlays can remain an optimization for the existing inheritance case; a cross-template selection should be an independent effective composition unless a formal projection contract is added. No resolver may merge Dashboard physical zones and marketing physical zones by position or silently carry incompatible widget configuration across templates.

### 6. Storage can support the clean contract, but identity and uniqueness need a deliberate decision

applicationLayouts.ts:719-909 already carries layoutId, zone, widgetKey, config, source configuration, source widget/base IDs, customization state, active state, and version. SchemaGenerator.ts:1140-1208 defines the application widget columns and lineage indexes, including a unique partial index for one inherited row per source base widget. Marketing instanceKey is currently kept inside JSON config, and stores/services validate duplicate keys in application code.

This is compatible with the no-schema-bump constraint if the new contract keeps identity in the existing envelope and does not add a second composition field. Row IDs remain persistence identities; stable semantic instance keys remain composition identities. React keys must be derived from persisted stable identities, not array indexes or randomly generated values, because widgets can be inserted, duplicated, deleted, and reordered.

The trade-off is that the database does not enforce unique marketing instanceKey directly. A clean plan must either:

-   retain transactional/application-level duplicate validation and add concurrency tests; or
-   prove that an existing JSON/index boundary can enforce the needed invariant without a schema or version change.

The plan must also explain how source_base_widget_id behaves for an independent cross-template layout. It must not manufacture an inherited source row merely to satisfy an index or make a Dashboard widget appear to be a marketing widget.

PostgreSQL's default Read Committed isolation does not make an application-only duplicate check race-proof. The plan must select an existing transaction, lock, or optimistic-version boundary, or prove an already available database-enforceable index path; serialization or unique conflicts must become typed, localized 409 responses. Because a schema bump is explicitly forbidden, the plan must document the remaining invariant limits instead of implying database enforcement that does not exist.

The API, seed, snapshot, store, and runtime boundaries should use strict Zod parsing and TypeScript discriminated unions for template/widget envelopes, with exhaustive handling of templateKey and widgetKey. safeParse failures must map to stable localized public error codes; raw validation text, object values, and internal identifiers must not escape into runtime or authoring UI.

### 7. Lifecycle coverage is strong for marketing, but not for the requested cross-template matrix

The current marketing-page tests cover much more than the original historical diagnosis suggested. marketing-page-widget-lifecycle.spec.ts verifies seeded instances and authoring operations. marketing-page-authoring.spec.ts and marketing-page-runtime.spec.ts cover application materialization, localized configuration, publication/sync, inactive widgets, route rendering, error/retry behavior, and leakage/overflow checks. marketing-page-snapshot-roundtrip.spec.ts and marketing-page-workspace-management.spec.ts cover import/export or reset-related behavior. marketing-page-visual.spec.ts covers locales, themes, and responsive viewports.

That evidence should be reused, not duplicated blindly. It does not prove:

-   metahub global Dashboard plus a Page/Object scoped marketing layout;
-   the inverse combination;
-   both hosted and standalone dispatch for an entity target;
-   application global and entity-scoped layouts with a different template from the metahub default;
-   precedence when metahub and application scopes both have candidates;
-   missing-base, mismatched-template, ambiguous-default, unknown-zone, or runtime-query-failure behavior;
-   publication, restore, snapshot roundtrip, and synchronization of a cross-template selection;
-   direct API/RBAC enforcement when the UI hides a different-template choice.

The standalone marketing runtime spec is conditional on an external shell/base URL and an application id. A skipped test in the default local environment is not evidence for the new standalone cross-template acceptance path.

### 8. Ownership and API boundaries from earlier research remain valid

The earlier research and implementation record correctly keep the isolated apps-template-mui package separate from the older template and legacy feature packages. That package should own MUI shell composition and template adapters, while types owns serializable contracts, metahubs owns canonical seed/default configuration, applications owns deployment materialization and authoring, and the runtime resolver owns authorized effective read models.

The existing SQL-first architecture remains a hard boundary. Backend work must continue through request-scoped DbExecutor/store modules, schema-qualified parameterized SQL, RLS/RBAC, UUID v7 identities, optimistic concurrency, and typed validation. A new resolver must not become a direct Supabase client path, a client-supplied table/column selector, or an authoring repair endpoint hidden inside a runtime read.

The earlier clean-break decisions also remain appropriate: use existing Hub/Object/Page/Set/Enumeration foundations, do not add a built-in entity kind for layout templates, keep canonical metahub content separate from application presentation and workspace CRUD, and do not add legacy readers or version bumps. The new brief supersedes only the earlier dashboard-only and same-template-only assumptions where it explicitly requires cross-template entity selection.

The apps-template-mui README is an important package boundary, not optional historical prose: it lists reusable detailsTable, relationBuilder, columnsContainer, cards, menus, row actions, and other dashboard primitives. A unified contract should preserve and reuse those primitives across compatible templates and adapters. It must not create a second one-off table/relation/action implementation merely to make a widget appear in marketing-page; capability sharing and visual composition sharing remain separate decisions.

### 9. MUI and accessibility guidance favors semantic regions with explicit shell behavior

The official MUI templates page presents Dashboard and Marketing page as separate starting points and notes that sections can be extracted and reused. This supports sharing widgets and capability contracts without requiring a universal renderer.

AppBar is a shell primitive for branding, navigation, and actions. When it is fixed, MUI requires the layout to account for the removed flow space, typically through a second Toolbar or theme mixin offset. A marketing navigation widget and a dashboard app bar should therefore share only a capability contract; they should not share an unexamined DOM wrapper or fixed-position assumption.

WAI landmark guidance requires meaningful header/banner, navigation, main, and footer/contentinfo regions, with accessible names when repeated landmarks exist. The semantic mapping should guarantee one clear top-level main region and avoid producing repeated unnamed navigation or footer landmarks when a layout contains multiple instances.

Responsive acceptance should be based on the selected template's composition primitives: Stack for one-dimensional regions, Grid for two-dimensional content, and explicit breakpoints/wrapping for repeated widgets. Existing project gates remain mandatory: localized labels and validation, keyboard operation and focus return for mobile navigation/dialogs, no raw IDs or JSON/object rendering, no page-level horizontal overflow, and safe URL/media/action handling.

### 11. UI Contract and browser oracle

The implementation plan needs a concrete UI Contract, not only a statement that the interface must be accessible. Authoring must provide localized global/entity-scope/template controls, human-readable entity and source choices, and explicit create, configure, duplicate, reorder, activate/deactivate, delete, reset, and conflict-confirmation actions using the existing application-layout list, card, dialog, and row-action primitives. System IDs, instanceKey, hashes, source IDs, physical table names, raw widget keys, and raw JSON must stay out of normal user-facing surfaces. Inherited, independent, inactive, missing, forbidden, stale, and conflict states must have localized labels and recovery actions. Long text must be multiline, and an optional empty resource source must be a deliberate quiet empty state rather than an error-looking blank control.

The runtime contract must expose semantic banner/header, navigation, main, and contentinfo regions with meaningful names when regions repeat. AppBar and Drawer controls must expose expanded/controls relationships and keyboard operation; mobile navigation and dialogs must return focus predictably. Each template needs a deliberate anchor/fixed-AppBar offset policy, a single clear main region, safe external URL/media/action handling, and no page-level horizontal overflow. A widget that is logically shared may still use a template-specific adapter and markup when those shell or accessibility requirements differ.

The browser oracle should follow the project's Playwright guidance: test user-visible behavior, isolate scenarios, prefer role/name or other user-facing locators with stable test IDs as supplemental selectors, and use awaited web-first assertions for asynchronous runtime state. The matrix must include RU and EN, hosted and standalone target dispatch, keyboard/focus, axe or equivalent landmark/accessibility assertions where useful, no raw ID/JSON/object leakage, no overflow, optional resource-source behavior, direct API/RBAC/CSRF negatives, and screenshot provenance/inspection for visual changes. A conditionally skipped external-shell test is not acceptance evidence.

## Conflicts And Uncertainty

-   The 2026-09-04 widgetized marketing research contains historical statements that the marketing renderer was fixed or that the seed had no widget assignments. The current checkout now has a persisted widget composition, nine seeded marketing instances, and lifecycle tests. Those statements are retained as diagnosis history, not current facts.
-   The 2026-09-04 implementation plan intentionally chose a dashboard-only registry boundary and same-template overlay assumptions. The current brief supersedes those assumptions for cross-template entity-scoped selection, but it does not require a universal renderer or make every widget shared.
-   The current marketing registry marks all listed marketing widget definitions repeatable. The new brief leaves repeatability as an open decision. PLAN must either ratify the existing all-repeatable behavior or deliberately narrow it with a new manifest rule and focused tests.
-   Sync and authoring validation generally rejects invalid template-zone combinations, while runtimeRowsController can omit top/bottom dashboard rows, filter unknown persisted zones before validation, and ignore loading errors. The plan must treat runtime fail-open behavior as a defect, not infer safety from the stricter sync path.
-   The public MUI pages currently identify a newer v9 release than the repository's exact MUI Core/System 9.2.0 catalog baseline. TypeScript, React, Playwright, TanStack Query, and Zod use catalog ranges; the current lockfile resolves at least TypeScript 5.9.3 and TanStack Query 5.90.21. Public documentation is used for current design/API guidance; catalog plus lockfile remain the implementation compatibility baseline. No package upgrade is implied by this research.
-   Existing visual and lifecycle evidence is strong for the marketing template, but the standalone test is conditionally skipped without its external shell. No current browser run in this RESEARCH task proves the new cross-template dispatch matrix.
-   The correct precedence between metahub global/entity, application global/entity, publication snapshot, workspace, route, and record content remains a product decision. In particular, a recordKey should not silently become a record-specific layout selector.
-   It is not yet decided whether a cross-template entity layout is self-contained or a formally compatible projection. The source code currently supports same-template inheritance and rejects template mismatch; it does not provide a safe answer for the new case.
-   The languageSwitcher decision is still open: share it only after both hosts expose the required locale, action, focus, and labeling capabilities, or reject the marketing placement explicitly. The matrix does not assume that a common widget key is sufficient.
-   The brief explicitly excludes a public/anonymous GuestApp contract unless separately specified, while leaving whether authenticated-only marketing is sufficient as an open PLAN decision. The current matrix covers authenticated standalone only and marks GuestApp DEFERRED; it does not authorize public transport or acceptance work.
-   Three advisory subagent reports were incorporated: architecture/source traceability, MUI runtime UX, and test-oracle completeness. Their conclusions were checked against direct source and are not treated as a substitute for executable tests.

## Recommended Decision

Proceed only to a decision-focused PLAN; implementation planning remains gated by the unresolved open questions. The provisional contract is:

1. Introduce a single effective-layout/template resolver that resolves the entity target before shell/renderer dispatch and is reused across runtime, publication, materialization, snapshot restore, and preview paths.
2. Keep Dashboard and marketing-page renderers separate. Define a neutral capability manifest and semantic placement vocabulary, then map each selected template to its physical zones. Share a widget only when host capabilities, data binding, focus behavior, and accessibility semantics are all satisfied.
3. Preserve physical storage fields and the no-version-bump constraint. Use the existing layout/widget/config/lineage fields with one authoritative composition envelope and stable instance identity. Do not add a second reader, a parallel composition field, or a legacy compatibility layer.
4. Keep same-template sparse inheritance as a separate mode. Make a cross-template entity selection self-contained by default; allow projection only after an explicit compatibility/provenance contract is specified and tested. Never silently inherit or reclassify incompatible widget data.
5. Make runtime selection fail closed on unknown zones, invalid template/widget combinations, missing mandatory data, ambiguous defaults, missing bases, database/query failures, and unauthorized targets. Preserve designed empty states only for explicitly optional or inactive widgets.
6. Repair the dashboard runtime transport so persisted top/bottom widgets are not lost and unexpected zones are not mapped to left. Align runtime behavior with the stricter sync normalization.
7. Keep the ownership split and SQL-first boundary from earlier research: metahub owns canonical definitions/seed, application owns deployment layout, workspace owns content, and the server owns effective resolution and physical IDs.
8. Add targeted tests for the new contract instead of resetting the existing marketing lifecycle evidence. The minimum browser matrix must cover metahub and application global/entity scopes, Dashboard-to-marketing and marketing-to-Dashboard selections, hosted and standalone dispatch, publication/snapshot/sync/restore, localized responsive UX, keyboard/focus behavior, and fail-closed errors.
9. Extend the existing query-key and invalidation helpers rather than creating a parallel cache namespace. Every changing runtime request input must be part of the key, and the effective-layout response/hash plus awaited invalidation must prevent a stale global bootstrap from rendering a target-specific template.

This decision satisfies the original task while avoiding the two unsafe extremes: duplicating every widget implementation in every template, or forcing both templates through one renderer with incompatible shell semantics.

## Open Questions Before PLAN

-   What is the exact precedence order among metahub global/entity layouts, application global/entity layouts, publication snapshots, workspace content, route targets, and record keys?
-   Does a Page/Object entity-scoped layout replace the global composition when its template differs, or must the product support a formally defined compatible projection?
-   Is an application global layout allowed to use a template different from the metahub global default, and how is that choice represented in the effective-layout response?
-   Which semantic regions are mandatory in the neutral contract: header, main, footer, sidebar, auxiliary, or a smaller set?
-   Which current Dashboard widgets can truly be shared, starting with languageSwitcher, and what locale/i18n, action, focus, and host-theme capabilities must each shared widget declare?
-   Should the current marketing policy of repeatable navigation, hero, pricing, and footer instances be retained, or should repeatability be per-widget manifest metadata?
-   Is layout template identity immutable for a layout while allowing a different template on a separate entity-scoped layout? What explicit UI/API operation creates the latter?
-   What are the localized user-facing states for invalid layout, stale lineage, missing base, ambiguous default, unauthorized target, and runtime query failure?
-   Does standalone mean authenticated application shell only for this slice, or should the separate brief for anonymous/public GuestApp be prepared later? Current acceptance is authenticated standalone only; GuestApp transport, authorization, caching, and browser acceptance remain DEFERRED until separately specified.
-   Which existing application/layout API response should carry target, scope, lineage, precedence, and hash so the client cannot render a stale template selected from a global bootstrap?
-   Which exact frontend response/schema/adapters and Dashboard rendering contract will carry top and bottom zones, and which zone names are canonical for each template?
-   Which variables must be present in runtime query keys and which layout/widget mutations must await targeted invalidation?
-   What transaction, lock, or optimistic-version guarantee is available for duplicate instance identity and stale lineage without a schema bump, and which conflicts map to 409?
-   Which existing package primitives are mandatory to reuse, and which documentation/provenance files must be updated when the approved contract changes?
