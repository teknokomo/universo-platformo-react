## Research Question

What is currently true in the repository about the machinery the MMOOMM economy MVP depends on, and which architecture decisions must PLAN make for the six open questions left by the brief plus the TZ's UI-first authoring requirement (RQ7):

1. **RQ1 (FR-019 proximity)** — how can a trade (sell/buy) be validated server-side for ship proximity to a station, given ship position is server-authoritative in the Colyseus room `FixedTickSceneRoom` and no REST↔room bridge exists?
2. **RQ2 (register entity kind)** — standard kind `ledger` entities via a template preset change (stakeholder TZ choice) vs object-kind entities with `ledgerSchema` capability + `config.ledger` (the production LMS pattern)?
3. **RQ3 (idempotency)** — idempotent Wallet creation + one-time StarterGrant + HTTP-level duplicate-submission protection for trade POSTs?
4. **RQ4 (economyPanel)** — module-backed widget vs fixed widget kind reading existing ledger REST endpoints?
5. **RQ5 (per-user scoping)** — how Wallet/Operation records and ledger projections are scoped per user, and whether projection queries leak other users' balances?
6. **RQ6 (error localization)** — where EN/RU economy error messages live (backend vs frontend)?
7. **RQ7 (generator authoring)** — the exact UI-first flows the E2E generator must replicate to author ledgers, posting config, and seed rows.

## Key Findings

### RQ1 — Server-side station proximity (FR-019)

Facts:

- The room is server-authoritative and identity-safe: `clientSessions: Map<sessionId, {client, userId, canControl, shipId}>` and `userShips: Map<userId, shipId>` (`packages/universo-react-applications-backend/src/realtime/applicationsRealtimeRuntime.ts:1211-1213`); userId comes from a Supabase JWT verified in the matchmake middleware, signed into HMAC room options with a one-time nonce, and validated in `onAuth` (`applicationsRealtimeRuntime.ts:987-990, 1008-1021, 1763-1786`). Room handlers can trust `ships → ownerUserId` without re-verifying tokens.
- Adding a trade message is mechanical: `onMessage('intent', …)` at `applicationsRealtimeRuntime.ts:1223-1234` and `onMessage('identify_local_ship', …)` at `:1236-1241` are the pattern; a third `market_trade` handler fits the same block. Rate limit `maxMessagesPerSecond = 30` (`:1218`) counts trades against the same budget.
- A distance check can literally mirror existing arrival logic: `remaining <= options.arrivalRadius` and `distanceVector3(nextPosition, target) <= options.arrivalRadius` (`packages/universo-react-colyseus-server/src/movement.ts:803, 852`).
- The Colyseus game server runs in the same Node process as Express: WebSocketTransport attached to the same HttpServer (`packages/universo-react-core-backend/src/index.ts:635-642`), `LocalPresence` (`applicationsRealtimeRuntime.ts:1887`), explicit single-process guard (`:1820-1822`).
- Server modules execute in-process (isolated-vm) and DB access flows through the caller's executor: `callInternalServerMethod` (`packages/universo-react-applications-backend/src/services/runtimeModulesService.ts:570-622`) builds a capability-gated context (`createExecutionContext` `:759-1004`: `records.list/get/findByCodename/create/update/delete` `:807-884`, `ledger.list/facts/query/append/reverse` `:933-999`, `callServerMethod` `:779-797`). `RuntimeModulesService` is already imported in the realtime module (`applicationsRealtimeRuntime.ts:34, 504`), and room-lifecycle code already queries the DB with `getPoolExecutor()` (`validateRuntimeAccess`, `applicationsRealtimeRuntime.ts:1026-1067`, called from `onJoin`/revalidation) — a DB-read precedent exists; a room→DB WRITE precedent does not yet exist.
- Workspace-enabled applications carry real PostgreSQL RLS on every runtime entity table: policies key on `app.current_workspace_id` (`packages/universo-react-applications-backend/src/ddl/applicationWorkspacesSchema.ts:445-475`), applied only when `workspacesEnabled` (`services/applicationSyncEngine.ts:840-856` per the sync path), and the context is set per-transaction via `set_config(..., true)` (`runtimeWorkspaceContext.ts:49-51`). A raw pool-executor write in autocommit therefore FAILS CLOSED on workspace-enabled apps; the write must run inside a transaction on a pinned connection that first calls `setRuntimeWorkspaceContext` — the in-repo precedent is `publicRuntimeAccess.ts:45-68` (pool executor + set_config inside transaction). The ledger fact INSERTs themselves do not read JWT claims (`appendFacts` uses explicit parameterized SQL with `_upl_created_by`/`workspace_id`, `runtimeLedgersService.ts:497-546`) and return 401 `LEDGER_ACTOR_REQUIRED` without `currentUserId` (`:490-495`) — the room handler must pass the member's Supabase UUID.
- Option (b) plumbing exists in Colyseus internals: the room sets `setMetadata({ scopeId })` and `filterBy(['scopeId'])` (`applicationsRealtimeRuntime.ts:1220, 1898`); `matchMaker.query({ name, scopeId })` filters by room fields + metadata and `matchMaker.getLocalRoomById(roomId)` / `remoteRoomCall` reach live local rooms (`@colyseus/core` 0.17.50 MatchMaker). Lifecycle risks: lazy room creation, `autoDispose = true` default, multiple rooms per application (scopeId embeds `applicationId:accessMode:workspace:objectCollection:widgetId:moduleKey`, `:638`), dispose races.
- Delivering `MarketRadiusMeters` into the room requires touching FOUR places coherently: `FixedTickSceneRoomOptions` interface (`:62-88`), `DEFAULT_ROOM_OPTIONS` (`:96-122`), the loader return with `clampNumber` (`:637-670`), and the `parseRoomOptions` whitelist (`:830-910`) — unknown fields are silently stripped and the HMAC signature is computed over the parsed values, so a missing field breaks joins entirely. Station position already rides `targetObjects` (fixture server module `tools/testing/e2e/support/mmoomm-app-export` + `tools/testing/e2e/support/mmoommAppGeneratorData.ts:30-63`).
- The widget's room connection is closure-local to the PlayCanvas canvas widget (`packages/universo-react-apps-template-mui/src/dashboard/components/playcanvasCanvasWidgetRuntime.ts:259, 601, 788`); there is no shared RoomContext. An economy panel would open its own `joinOrCreate` (same scopeId → same room, same per-user ship — `getOrCreateShipForUser` `applicationsRealtimeRuntime.ts:1548-1560`).
- EconomyConstants-style fixed values are NOT a queryable constants API: set fixed values materialize as field-value references on entity rows (`packages/universo-react-applications-backend/src/services/publishedApplicationSnapshotEntities.ts:166-183`); a server module reaches them only via `ctx.records`.
- Public `accessMode` rooms may have `currentUserId` null (`:681-689`) and only members can control ships (`:872`) — the ownership/wallet model is well-defined only in member mode.

Inference: both (a) room-message trade and (b) same-process REST↔room bridge are feasible; (a) keeps one trust domain and has no dispose race but needs new room→DB-write plumbing (de-risked by `validateRuntimeAccess` and the in-process isolated-vm path); (b) has the easiest E2E (plain `request.post`) but must handle room-absent/dispose races and scopeId recomputation. (c) client-declared proximity is spoofable by construction. For option (a) on workspace-enabled applications the trade write must set the runtime workspace context inside its transaction (RLS fails closed otherwise); economy stays member-mode by construction (`appendFacts` requires `currentUserId`).

### RQ2 — Register entity kind

Facts:

- Runtime qualification is kind-agnostic. `LEDGER_CAPABILITY_CONDITION` (`packages/universo-react-applications-backend/src/services/runtimeLedgersService.ts:84-90`):
  `config->capabilities->ledgerSchema.enabled = true AND dataSchema.enabled = true AND physicalTable.enabled = true AND jsonb_typeof(config->'ledger') = 'object'` (+ not-deleted). The `kind` column is selected but never filtered (`:259-311`, `:1028-1039`); an exact duplicate of the predicate exists in `runtimeModulesService.ts:66-72`, and `loadRuntimeObjectSeedMetadata` carries a negated variant that additionally requires `sourcePolicy = 'registrar'` (`applicationWorkspaces.ts:906-911`). Both variants qualify.
- `config.capabilities` is stamped from the entity TYPE definition when the snapshot materializes (`mergeEntityTypeRuntimeConfig`, `packages/universo-react-applications-backend/src/services/publishedApplicationSnapshotEntities.ts:95-111`), so kind determines capabilities indirectly.
- A ledger-kind entity cannot be a registrar: `LEDGER_TYPE_CAPABILITIES.posting: false, records: false` (`packages/universo-react-metahubs-backend/src/domains/templates/data/standardEntityTypeDefinitions.ts:261, 277`). In both variants the registrar is the `Operation` object with `recordBehavior.posting`; `registrarKind = objectCollection.kind` (`.../controllers/runtimeRowCommandHandlers/posting.ts:124-130`), and empty `registrarKinds` allows all kinds (`runtimeLedgersService.ts:125-137`).
- LMS precedent (variant B in production): seed entities are `kind: 'object'` with full `config.ledger` (`buildLmsBalanceLedger`, `packages/universo-react-metahubs-backend/src/domains/templates/data/lms.seed-entity-helpers.ts:96-148`; `lms.seed-entities.initial.ts:561-600, 694`); the LMS template does NOT include the ledger preset (`lms.template.manifest.ts:49-55`); the LMS snapshot contract requires `kind === 'object'` + `config.ledger` (`tools/testing/e2e/support/lmsSnapshotEnvelopePagesContract.ts:86-129`).
- Variant A side effects: adding `{ presetCodename: 'ledger', includedByDefault: true }` to `playcanvas.template.ts:34-41` seeds, in EVERY new playcanvas-template metahub, the ledger type definition + the default instance `Main` (6 components, `LEDGER_DEFAULT_INSTANCES`, `standardEntityTypeDefinitions.ts:467-514`; merge at `MetahubSchemaService.ts:751-787`; its `LEDGER_TYPE_CONFIG = { ledger: DEFAULT_LEDGER_CONFIG }` at `:291-293` is what makes `Main` satisfy the runtime capability condition and appear in `GET /runtime/ledgers`). `Main` does NOT appear in generated menus (runtime menu built from kind `hub|page|object` only — `effectiveWidgetRuntimeMenu.ts:36`; `trustedLayoutResolver.ts:24`; `applicationWorkspaces.ts:904-911` exclude kind 'ledger') and MMOOMM contracts do not notice it, but it WILL appear in `GET /runtime/ledgers` of every published application, and the canonical MMOOMM fixture drifts → regeneration is required in any case. Manifest/registry safety (TZ §16 Q1): the preset line must be appended at the END of the presets array (`projectPresetTemplate.test.ts:75-84` pins `presets[0] === 'project'`); the standard ledger preset is already registered in the template registry (`templates/data/index.ts:47`), so manifest validation is not a blocker.
- `presetToggles` are all-or-nothing per preset (`buildEffectivePresetToggles`, `MetahubSchemaService.ts:737-749`; `:885-888` filters enabledPresets before manifest load) — there is no "type without default instance" option. Snapshot-import flows are isolated: import creates metahubs with ALL presetToggles false (`metahubsController.ts:2199-2228`).
- Existing playcanvas-template metahubs: explicit migration apply syncs the new type AND inserts `Main` (persisted toggles lack the 'ledger' key → fallback `includedByDefault` → true; `syncTemplateSeed` `MetahubSchemaService.ts:1170-1206`; `TemplateSeedMigrator.ts:429-448` skip-existing). A deleted `Main` can resync on structure migrations.
- Variant B authoring is UI-proven twice: template-level (LMS) and via the Entity Type Constructor with ledgerSchema (`tools/testing/e2e/specs/flows/metahub-entities-workspace.spec.ts:366-396`). The "Ledger schema" tab appears for plain object entities (condition at `EntityInstanceListContent.tsx:477-481`; `OBJECT_TYPE_UI.tabs` includes `ledgerSchema`, `standardEntityTypeDefinitions.ts:131`), and the posting-target dropdown already lists object-ledger candidates (`ObjectCollectionList.tsx:228-267`).
- Architecture rule: the `universo-platform-architecture` skill blocks adding a separate Ledger entity unless the registered template explicitly requires it and frames the Ledger preset as the future 1C-compatible template's alternative (`SKILL.md` blocking rules; no built-in template uses the ledger preset today — the implemented 1C-compatible template uses its own presets, `one-c-compatible.template.ts:36-51`).

Inference: variant B (object-kind + `ledgerSchema`) matches the architecture skill directly, needs no template change, and is the double-proven pattern; variant A is justifiable only through the template-opt-in exception and drags the `Main` side effect. A hybrid exists (seed kind-`ledger` entities WITHOUT the preset — the type syncs via seed-kind reference, `MetahubSchemaService.ts:890-897`) but still makes MMOOMM the first non-1C user of the reserved kind. The decision belongs to the stakeholder (the TZ chose A; the platform rule prefers B).

### RQ3 — Wallet / StarterGrant / HTTP idempotency

Facts:

- No user-declared SQL unique constraint exists on component columns: column generation handles only `notNullable`/`defaultTo` (`packages/universo-react-schema-ddl/src/SchemaGenerator.ts:144-163`); metahub design-time records live in `_mhb_elements` JSONB (`MetahubRecordsService.ts:503, 539-547`). Design-time uniqueness is application-level: `validationRules.unique = true` + `assertUniqueComponentValues` inside the write transaction with an advisory lock (`MetahubRecordsService.ts:817-847, 126-129`).
- At application RUNTIME (physical tables) there is no app-level unique check — the only DDL unique index derived from entity config is the ledger idempotency partial index (`ensureLedgerIdempotencyIndex`, `packages/universo-react-applications-backend/src/ddl/applicationWorkspacesSchema.ts:408-438`, only for ledger-capable entities per `entityCapabilities.ts:289-296`).
- Server-module context CAN create records and append facts inside the caller's transaction: `ctx.records.create` runs inside `params.executor.transaction(...)` (`runtimeModulesService.ts:1315-1481`), and request transactions propagate into lifecycle dispatch with SAVEPOINTs (`packages/universo-react-database/src/knexExecutor.ts:61-63, 105-149`; `posting.ts:189-203` → `runtimeLifecycleDispatch.ts:38-56`). So a `beforePost` module can ensure-a-wallet and append movements atomically — but it has no create-if-missing primitive; the advisory-lock serialization is available to backend code, not to modules.
- `source_row_id` is NOT automatic: the `beforePost` module composes facts itself from `payload.previousRow.id` (LMS precedent: `packages/universo-react-modules-engine/src/compiler.test.ts:51-57`).
- An HTTP idempotency precedent EXISTS end-to-end — the guest-session intake: `parseGuestIdempotencyKey`/`hashGuestIdempotencyKey`/`fingerprintGuestIntakePayload` (`packages/universo-react-applications-backend/src/services/guestSessionIdempotency.ts:28-59`), header read at `controllers/runtimeGuest/guestSessionIntake.ts:106-110`, replay-vs-conflict at `guestSessionReplay.ts:43-48`, 409 at `guestSessionHandler.ts:149-154`, keyed advisory lock at `:93`, persistent store with `idempotency_key_hash VARCHAR(64) NOT NULL UNIQUE` + expiry purge (`platform/migrations/1800000000300-CreateGuestSessionIdempotency.sql.ts`, `guestSessionHandler.ts:130`). This is the exact-fit precedent for `ECONOMY_IDEMPOTENCY_CONFLICT` semantics (same key+body → replay; same key+different body → 409).
- Economy MVP machinery (wallet/StarterGrant/economy services) is greenfield: no `wallet`/`StarterGrant` strings exist in packages/tools source. One pre-existing semantic hook must NOT be overlooked: the net protocol already defines a typed `'economy.transfer'` event `{ from, to, currency, amount, ref? }` with a validation schema (`packages/universo-react-types/src/net/events.ts:6`; `packages/universo-react-utils/src/validation/schemas.ts:52`) — a natural transport for trade notifications if PLAN wants one, but no economy logic exists behind it.

Inference: Wallet uniqueness should use the check-then-create pattern under an advisory transaction lock (mirroring `assertUniqueComponentValues`), implemented in the economy service at runtime; making Wallet ledger-capable just to reuse the idempotency index is semantic overload. StarterGrant is a `beforePost` module over the existing posting pipeline. HTTP idempotency ports the guest-intake pattern (hash key, HMAC body fingerprint, keyed lock, replay table).

### RQ4 — economyPanel implementation shape

Facts:

- Widget-role capability ceiling: `widget` modules are allowed only `['metadata.read', 'rpc.client']` (`packages/universo-react-types/src/common/modules.ts:110`) — a widget module can NEVER read ledgers; `callServerMethod` resolves methods on the SAME module only (`runtimeModulesService.ts:779-797`). The PlayCanvas pattern (widget module + separate `serverModuleCodename` invoked backend-internally) is a bespoke per-widget-kind backend integration, not a generic channel.
- Client modules run in a browser Web Worker sandbox (`packages/universo-react-apps-template-mui/src/dashboard/runtime/browserModuleRuntime.ts`) with shadowed globals; server modules run in isolated-vm (32 MB, 500 ms default timeout, `packages/universo-react-modules-engine/src/runtime.ts:571-625`).
- There is no generic module-hosted UI renderer: QuizWidget and PlayCanvasCanvasWidget render fixed per-kind UI; modules only supply data (`QuizWidget.tsx:215-216, 274-421`).
- The generic read path already exists: `POST /:applicationId/runtime/ledgers/:ledgerId/query` and `GET .../projections/:codename` (`applicationsRoutes.ts:237-242`) → `queryProjection` (`runtimeLedgersService.ts:362-465`), client fetchers with Zod validation `fetchRuntimeLedgerFacts`/`fetchRuntimeLedgerProjection` (`packages/universo-react-apps-template-mui/src/api/api.ts:690-744`).
- Widget plumbing for a new kind: config schema (`dashboardWidgetConfigSchemas.ts:516-669`), registry entry (`dashboardWidgetRegistry.ts:593-633`; `playcanvasCanvas` is center-only `:607-633`; `resourcePreview` is the `{dashboard: ['center','right']}` precedent), renderer case (`widgetRenderer.tsx:319-324`), editor dialog (`LayoutWidgetEditorDialogs.tsx:66-73` pattern), i18n, registry parity tests.
- Module authoring via UI exists and is E2E-proven: Modules tab (CodeMirror) → `POST /api/v1/metahub/:metahubId/modules`; generator helper `createRuntimeModuleThroughBrowser` pastes source into `testid=entity-modules-editor-shell` (`.cm-content`) and waits for the POST (`tools/testing/e2e/support/mmoomm-app-export/metahub-authoring.ts:523-627`).

Inference: option (a) — a fixed `economyPanel` widget kind reading the existing projection REST endpoints, with config selecting ledger codenames, projection codenames, and filters — is the only shape fully served by existing platform pieces, is FR-031-compliant (declarative projections, no SQL), and keeps E2E authoring at layout-placement complexity. Pure module-backed (b) is structurally blocked by the widget-role ceiling; (c) requires a greenfield generic module-UI host. Sell/buy actions remain route/module work (RQ1/RQ3), not panel work. Balance reads for the panel route through the FR-021 summary service per RQ5 — the projection REST path is the transport shape, not the security boundary.

### RQ5 — Per-user scoping (and a security gap)

Facts:

- `runtimeRecordAccess` config schema lives in applications-backend: `{ mode: 'ownerOrShared' | 'ownerOnly', ownerFieldCodename?, ownerColumnName?, sharedRelationKey }`, strict, fail-closed on invalid config (`packages/universo-react-applications-backend/src/services/runtimeRowSupport/contracts.ts:451-472, 522-525`).
- Enforcement is fail-closed and covers list/get/update/delete/restore/copy/reorder AND the posting command (`buildRuntimeRecordAccessClause`, `runtimeRowSupport/access.ts:522-603`; `posting.ts:147-159` uses `minimumAccessLevel: 'edit'`). `ownerOnly` is NOT bypassed even by `manageApplication`. CREATE is NOT enforced and the custom owner field is NOT stamped automatically — but `_upl_created_by` IS auto-stamped on create (`create.ts:515-519`) and exists on every entity table (`SchemaGenerator.ts:494`).
- The stable per-user key is the Supabase auth UUID (`req.user.id` = `auth.users.id`, `packages/universo-react-auth-backend/src/passport/index.ts:24`; resolved by `resolveUserId`, `runtimeHelpers.ts:744-748`). The LMS precedent uses `ownerColumnName: '_upl_created_by'` (`lms.seed-entities.tracks.ts:46-50`).
- There is NO UI for runtimeRecordAccess — it is backend/template-seed config only.
- **Security gap**: `POST /:applicationId/runtime/ledgers/:ledgerId/query` AND `GET .../ledgers/:ledgerId/facts` call `resolveRuntimeSchema` WITHOUT `ensureRuntimePermission` (`runtimeLedgersController.ts:96-131` for query and `:63-94` for facts — unlike appendFacts/reverseFacts/updateFact/deleteFact which require content permissions), and `queryProjection` filters are CLIENT-supplied over any declared field (`runtimeLedgersService.ts:362-465`, `:402-421`). The only server-side isolation is `workspace_id` (when the workspace column exists and `currentWorkspaceId` is set, `:229-235`). Therefore user A can query user B's balance by passing B's WalletKey (within the same workspace, or fully if workspaces are disabled).

Inference: the economy MVP must NOT let the panel query balances through raw client-filtered projection queries. The TZ's `GET /runtime/economy/summary` (FR-021) is the right vehicle: a server-side economy service injects the current principal's dimension values and computes balances/cargo/operations server-side. `Wallet`/`Operation` records use `runtimeRecordAccess { mode: 'ownerOnly', ownerColumnName: '_upl_created_by' }`. The projection-query permission gap should at minimum be flagged for a platform-level fix (add permission checks and/or server-side filter injection), independent of the economy.

### RQ6 — Error localization

Facts:

- Backend shape: `UpdateFailure(statusCode, body)` with body `{ error: string, code?: string, ...details }` (`packages/universo-react-applications-backend/src/shared/updateFailure.ts:2-6`); controllers rethrow as `res.status(...).json(...)` (`runtimeLedgersController.ts:88-93, 122-128`; `runtimeHelpers.ts:1017-1021`). Concrete throws: `{ error: 'Record posting is disabled…', code: 'POSTING_DISABLED' }` (`posting.ts:120-122`), `{ error: 'Ledger accepts facts only from registrar posting flows', code: 'LEDGER_REGISTRAR_ONLY' }` (`runtimeLedgersService.ts:113-118`).
- Frontend: `AppsApiError` carries `code` (`packages/universo-react-apps-template-mui/src/api/client.ts:151-163, 180-208`).
- Code→i18n precedents: `LAYOUT_RUNTIME_ERROR_CODES` whitelist + `t('runtime.layoutErrors.<code>', { defaultValue: t('runtime.loadError') })` in RuntimeBoundary (`packages/universo-react-types/src/common/applicationLayouts.ts:181-194`; `apps-template-mui/src/standalone/DashboardApp.tsx:790-830, 904-912`; dictionaries `src/i18n/locales/en/apps.json:578-589` and `ru/apps.json:578-589`), and `errorKeyByCode` mapping in `useCellMutations.ts:251-269`.

Inference: established pattern = backend returns stable English `code` + message; frontend maps `code` → localized text via an i18n dictionary with English fallback. For economy: add `ECONOMY_*` codes to a types whitelist, throw `UpdateFailure` with those codes, and add `runtime.economyErrors.*` (en/ru) to apps.json.

### RQ7 — UI-first authoring flows for the generator

Facts:

- Ledger schema tab: fields are mode (`facts|balance|accounting|calculation`), mutationPolicy (`appendOnly|manualEditable`), sourcePolicy (`manual|registrar|both`; `manual` hidden without `allowManualFacts`), periodicity (`none|instant|day|week|month|quarter|year`), effectiveDateField, registrarKinds (multi-select), fieldRoles (field + role + aggregate, picked from EXISTING components — empty in the create dialog, hint "Create fields first…"), projections (codename + kind + dimensions/resources entered as CSV TEXT), idempotency keyFields (CSV) (`packages/universo-react-metahubs-frontend/src/domains/entities/ui/LedgerSchemaFields.tsx:135-495`).
- Persistence: create → `POST /api/v1/metahub/:metahubId/entities/object/instances` with `config.ledger`; update → `PATCH /api/v1/metahub/:metahubId/entity/:entityId` with `config` + `expectedVersion` (`EntityInstanceListContent.tsx:932-1050`; `presets/api/objectCollections.ts:189-225, 296`). Validation on both sides (`validateLedgerConfigReferences`, `ObjectCollectionActions.tsx:481-533`; backend `entityControllerShared.ts:383-413`).
- Behavior tab (recordBehavior/posting): mode select, posting.mode (gated by capabilities), posting.targetLedgers multi-select — populated ONLY from entities that already have `config.ledger` (hint "Create a Ledger entity before selecting targets."; `ObjectCollectionList.tsx:228-267`, `RecordBehaviorFields.tsx:497`), posting.moduleCodename, effectiveDate.fieldCodename, lifecycle states with `isInitial` required (`RecordBehaviorFields.tsx:345-430`; validation `ObjectCollectionList.tsx:103-125`).
- NO data-testid exists inside LedgerSchemaFields/RecordBehaviorFields — selectors must use MUI label/role, or testids must be added (frontend change).
- Seed ROWS: existing generators do NOT create rows via UI (no records grid in metahub authoring); they use `createRecord(api, metahubId, objectId, payload)` → `POST /api/v1/metahub/:metahubId/entities/object/instance/:objectId/records` (`tools/testing/e2e/support/backend/api-session.mjs:1088-1101`; usage `specs/generators/metahubs-lms-app-export.spec.ts:209-270`). The `createStandardEntityThroughBrowser` helper supports only General(+Navigation) tabs — Ledger/Behavior tab steps are new work.
- Ordering constraints: create object → create its components → reopen edit dialog → fill Ledger schema (roles need components) → save; the register must be saved BEFORE posting targets can be selected on the Operation object.

Inference: the generator needs new authoring helpers for the Ledger schema and Behavior tabs (order-sensitive: components first, register saved before posting targets become selectable) plus seed rows via `createRecord`; the selector strategy (label/role vs new testids) is the only frontend-facing decision, carried as Open Question 4.

## Conflicts And Uncertainty

1. **TZ decision vs architecture rule (RQ2)** — the stakeholder TZ chose standard kind `ledger` entities + template preset (FR-001, FR-009/FR-010); the `universo-platform-architecture` skill's blocking rule reserves the Ledger preset for the future 1C-compatible template and requires Object+recordBehavior in base templates. Both runtime paths are functionally equivalent (kind-agnostic gating). This is a genuine stakeholder decision, not a technical blocker. Hybrid (kind-`ledger` seed entities without the preset) noted.
2. **Projection query permission gap (RQ5)** — client-filtered projection queries without per-user injection or permission checks would leak other users' balances; the economy design must route balance reads through the server-side summary service, and the platform gap itself deserves a tracked fix.
3. **No room→DB write precedent (RQ1)** — option (a) requires new plumbing (room handler → `callInternalServerMethod`); de-risked by the existing DB-read precedent (`validateRuntimeAccess`) and in-process isolated-vm, but it is new code. On workspace-enabled applications the write MUST run inside a transaction that sets the runtime workspace context first (`setRuntimeWorkspaceContext`, precedent `publicRuntimeAccess.ts:45-68`) or PostgreSQL RLS rejects it fail-closed; with workspaces disabled a plain pool executor suffices. Per steering §2.4 this is Tier 2 execution — per-user isolation must be enforced application-side, not by RLS.
4. **`parseRoomOptions` HMAC coupling (RQ1)** — any new room option field must be added in four places or joins break with signature mismatch; easy to miss in PLAN.
5. **Public access mode (RQ1)** — `currentUserId` may be null in public rooms; the wallet model is well-defined only for member-mode rooms. The MVP should scope economy to member mode (consistent with the TZ's "authenticated runtime user" requirement).
6. **Colyseus freshness** — current docs lead with v0.18 (released 2026); the repo pins 0.17.50. Upgrades are out of scope per the TZ; 0.17 API facts above were verified against the installed package/majority-stable APIs.
7. **No testids in Ledger/Behavior tab internals** — E2E generator either selects by label/role or adds testids (frontend change outside research scope).
8. **HTTP `Idempotency-Key` standard status** — IETF WG draft (-07/-08), not yet an RFC; MDN documents the header. Using the header name is safe (mainstream adoption); semantics implemented locally per the guest-intake precedent.

## Recommended Decision

1. **Registers: variant B** — object-kind entities with `ledgerSchema` capability + full `config.ledger` (fieldRoles/projections/registrarKinds configured like the LMS seeds), no template change. Aligns with the architecture skill, double-proven (template-level LMS + constructor E2E), zero `Main` side effect. Requires explicit stakeholder confirmation because the TZ chose variant A; the hybrid (kind-`ledger` seeds without the preset) is the fallback if the stakeholder insists on the ledger kind.
2. **Proximity: option (a)** — trade as a room message `market_trade` handled in `FixedTickSceneRoom`: validate `distanceVector3(shipRuntime.movement.position, targetObjects[stationId]) <= marketRadiusMeters` (mirroring `movement.ts:852`), then invoke the economy/posting machinery via `callInternalServerMethod` with `getPoolExecutor()` (in-process, member mode only). `marketRadiusMeters` enters roomOptions through the server-module `createRealtimeRoomOptions` path with the four-place roomOptions plumbing. Option (b) (REST↔room bridge via `matchMaker.query`/`getLocalRoomById`) is the documented fallback with the easiest E2E but dispose-race and scope-recomputation complexity. `summary` stays REST in both cases. Convention caveats: the room-side trade write runs on the Tier 2 pool executor (no request RLS context) — per-user isolation must be enforced application-side (server-resolved principal, `runtimeRecordAccess ownerOnly`, registrar-only ledger policy, in-`beforePost` validation), and on workspace-enabled apps the write transaction must call `setRuntimeWorkspaceContext` first (RLS fails closed otherwise, precedent `publicRuntimeAccess.ts:45-68`); the REST `summary` route uses the Tier 1 request executor `getRequestDbExecutor(req, getDbExecutor())` per `.kiro/steering/recommendations.md` §2.4.
3. **Wallet/StarterGrant** — plain `Wallet` object; economy service ensures one wallet per user with check-then-create under an advisory transaction lock (mirroring `assertUniqueComponentValues`); StarterGrant is a `beforePost` posting module composing facts with `payload.previousRow.id`; ledger idempotency keyFields enforce fact-level one-time semantics.
4. **HTTP idempotency** — port the guest-session intake pattern (hashed key + HMAC body fingerprint + keyed advisory lock + replay store with purge; same key+same body → replay, same key+different body → 409 `ECONOMY_IDEMPOTENCY_CONFLICT`), accepting the standard `Idempotency-Key` header.
5. **economyPanel** — fixed widget kind whose data source is the FR-021 `GET /runtime/economy/summary` endpoint (server-side per-user injection), covering balance, cargo, capacity, market prices, and recent operations; trade buttons call the economy routes; generic projection endpoints (`fetchRuntimeLedgerProjection`) may serve only non-user-scoped displays, or everything after the platform-level per-user injection fix (Open Question 3) — the panel never queries balances through raw client-filtered projection queries and never renders raw IDs.
6. **Per-user scoping** — `Wallet`/`Operation` carry `runtimeRecordAccess { mode: 'ownerOnly', ownerColumnName: '_upl_created_by' }` (auto-stamped, LMS precedent); balances are computed server-side by the economy summary service (FR-021), never exposed through raw client-filtered projection queries; flag the projection-query permission gap as a platform follow-up.
7. **Errors** — stable `ECONOMY_*` codes in `UpdateFailure` bodies; frontend maps codes → `runtime.economyErrors.*` i18n (en/ru) with English fallback.
