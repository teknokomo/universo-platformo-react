## Research Question

What is currently true in the repository about the machinery the MMOOMM mining MVP depends on, and which architecture decisions must PLAN make for the six open questions left by the QA-refined brief, plus the residual checks the brief deferred:

1. **RQ1 (brief OQ1)** — `StationCode` on the `Mine` inventory fact: how does the implemented trade flow resolve the station today, and what should the fire flow stamp without touching the ledger structure?

3. **RQ3 (brief OQ3)** — per-user cooldown mechanism: advisory-lock + last-Mine query vs an idempotency-store row; what is the cooldown source given `LastMinedAt` is per-asteroid but TZ §9.5 makes cooldown per-user?
4. **RQ4 (brief OQ4)** — idempotency extension for `fire`: kind schema, request/response schemas, migration needs.
5. **RQ5 (brief OQ5)** — client target-vs-fly semantics: how do asteroid meshes become pickable-without-flyable, what breaks, and what is the minimal-risk targeting design?
6. **RQ6 (brief OQ6)** — `MiningConstants` resolution and state-GET caching.

Residual: where the mining service lives (`postOperationRow` is a closure), how `MINING_*` error codes flow to the client i18n, the `DATE` vs `DATETIME` authoring question for `LastMinedAt`, the TZ-assigned line-of-sight decision (§9.2/§16-Q5), laser/chunk entity lifecycle, HUD mount point, polling gating, and TZ §9.3/§9.4 transaction-and-chunk specifics PLAN must carry verbatim.

## Key Findings

### RQ1 — Station resolution and the `Mine` fact's `StationCode`

Facts:

- Trade resolves proximity via `resolveStationProximity` (`packages/universo-react-applications-backend/src/services/runtimeEconomySupport.ts:555-586`): calls `describeFlightContext(applicationId, userId, workspaceId)` (:561), filters bridge `flight.stations` by 3D distance against `economy.marketRadiusMeters` (:564-567), fails `ECONOMY_NOT_AT_STATION` otherwise (`runtimeEconomyService.ts:618-624`).
- Room station ids are **widget scene object ids**, not row ids: `describeShipForUser` maps `roomOptions.targetObjects` into `{ id, position }` entries (`applicationsRealtimeRuntime.ts:1222-1242`; `FlightStationTarget` at `runtimeFlightRoomBridge.ts:5-8`). The resolver therefore falls back: `loadStationRowByIds` by id (`ORDER BY _upl_created_at ASC NULLS LAST, id ASC`, `runtimeEconomySupport.ts:400`), else `loadFirstStationRow` — a bare `WHERE <active> LIMIT 1` over FlightStation rows with **no ORDER BY** (`:414-453`, query `:430-441`).
- The chosen station id lands on the Operation row as `Station: proximity.stationId` (`runtimeEconomyService.ts:705`); the posting module then reads `operation.Station` by codename (`mmoommAppGeneratorData.ts:179`), loads the station row via `ctx.records.get('FlightStation', …)` (`:201-218`), and stamps the fact as `stationCode = readText(station, 'Code') ?? stationRefId` (`:218`), applied at `:278`. The fixture's `FlightStation` has **no `Code` component** (only `MarketEnabled`/`MarketFeePercent`, `metahub-authoring.ts:1512-1515`), so today's `StationCode` fact value is effectively the FlightStation row UUID.
- Fire does NOT need the at-station requirement: mining happens at the belt. The ledger dimension just needs a non-null station identifier, and the MVP has exactly one station.

Inference: the fire flow reuses the *fallback half* of the trade station resolution — `loadFirstStationRow` (single-station MVP) — inside the fire transaction, and the Mine module stamps `StationCode` with the same `Code ?? rowId` derivation the trade module already uses. No ledger-structure change; TZ §7.5 default satisfied. The stamped station is **not surfaced in the mining UI in MVP** (it is an internal ledger dimension; the state endpoint may expose it for context but FR-022 does not require it). Authoring a `FlightStation.Code` STRING component is an optional data-quality improvement, not a requirement.

### RQ2 — `OperationKind` branching and the contract cascade

Facts:

- The module source lives in `tools/testing/e2e/support/mmoommAppGeneratorData.ts:95-294`; it is authored through the Modules UI with `sourceCode` + capabilities `['lifecycle','metadata.read','records.read']` and re-attached to the Operation object (`metahub-authoring.ts:1353-1374`).
- Compilation: `MetahubModulesService.compileSource` → `compileModuleSource` → esbuild `bundleSource` (`packages/universo-react-modules-engine/src/compiler.ts:1044-1115`); `serverBundle` is stored on module create/upsert/recompile (`MetahubModulesService.ts:706,767,910`), carried by the snapshot serializer (`SnapshotSerializer.ts:755`) into `_app_modules.server_bundle` at app sync (`syncModulePersistence.ts:272-273`). Regenerating the fixture recompiles the module automatically.
- `payload.previousRow` exposes **raw `cmp_<fieldId>` columns + system columns**, not codenames (`posting.ts:166-203`; documented `runtimeEconomyService.ts:78-84`). Codename-keyed values come from the module Record API `ctx.records.get(entityCodename, rowId)` — `buildModuleRecordPayload` keys values by codename with NUMBER coercion (`runtimeModulesService.ts:285-301`). The module already reads `Quantity/UnitPrice/TotalPrice/Station/Wallet/Nomenclature` this way (`mmoommAppGeneratorData.ts:170-218`).
- Therefore the new server-owned `OperationKind`/`AsteroidCode` STRING components need **no posting-core change**: once authored, the module reads them by codename via `ctx.records.get` exactly like the existing fields, and the kind heuristic (`unitPrice === 0 → starterGrant`, `mmoommAppGeneratorData.ts:227`) gains a precedence branch: `kind === 'Mine'` → Mine rules; absent → existing heuristic (TZ §10.2–10.3 fallback).
- Contract side: `assertEconomyDomainModel` (`tools/testing/e2e/support/mmoommAppContentContract.ts:340-436`) pins required economy objects, exact enum value lists (`MMOOMM_ECONOMY_OPERATION_TYPE_VALUES` already contains `'Mine'`, `mmoommAppFixtureContract.shared.ts:77`), ownerOnly access on Wallet/Operation, and posting config **targeting both registers** (`mmoommAppContentContract.ts:408-414`; authoring poll `metahub-authoring.ts:1474-1497`, both-targets check `:1488-1493`). Additive edits: new codename constants (`mmoommAppFixtureContract.shared.ts`), Asteroid/AsteroidStatus/MiningConstants in `assertDomainModel`/`assertEconomyDomainModel`, serverOwned assertions for the new fields, and the "exactly two primary-nav objects" check must keep excluding Asteroid (`~:218-243`).

Inference: `targetLedgers` stays `[WalletLedger, InventoryLedger]` (per-record config on the shared Operation entity — narrowing per kind is not expressible and would break `Sell`/`Buy` + the contract); the `Mine` branch returns only the InventoryLedger movement group, which `assertDeclaredLedgers` already permits (verified in the brief's QA). The Mine branch validates `Quantity > 0`, `UnitPrice === 0`, `TotalPrice === 0`, `AsteroidCode` set, and throws (rollback) otherwise — TZ §10.2.

### RQ3 — Per-user cooldown mechanism

Facts:

- TZ §9.5 makes cooldown **per-user** ("Cooldown проверять по пользователю, а не по астероиду" — cooldown is checked per user, not per asteroid), while `Asteroid.LastMinedAt` (TZ §7.2) is per-asteroid state. A user firing at `AST-01` then `AST-02` must still be cooldown-limited, so `LastMinedAt` cannot be the cooldown source.
- The implemented per-user serialization precedent is the advisory lock `acquireAdvisoryXactLock(executor, `${applicationId}:${ctx.userId}:${currency}`)` before balance reads (`runtimeEconomyService.ts:629`; helper `locks.ts:20-22`).
- A "user's last Mine operation" query has an exact in-repo template: the StarterGrant once-only check `SELECT id FROM <operation table> WHERE <ownerCol> = $1 AND <typeAttr col> = $2 LIMIT 1` (`runtimeEconomyService.ts:470-479`), and the recent-operations read `buildRecentOperations` with the belt-and-braces owner clause `_upl_created_by = $n` (`runtimeEconomySupport.ts:592-692`, owner clause at `:617-618`).
- `_upl_created_by` exists on every entity table (`SchemaGenerator.ts:494`) but **has no index** anywhere in schema-ddl or platform migrations (verified by grep: only `_upl_deleted_at`/`_app_deleted_at`/`_app_owner_id`/record-state/posted-at partial indexes, `:303-313,515-531`). A per-user "last Mine" query is a seq scan on the per-application Operation table — small at MVP scale.
- The idempotency store is keyed `(application_id, user_id, key_hash)` and only stores successful fire responses — it is a replay store, not a cooldown store; reusing it for cooldown would be semantic overload (the same reasoning RES-2026-014 used against making Wallet ledger-capable).
- Table naming context: `naming.ts:11` (`object: 'obj'`), `generateTableName` at `:29-33`; the runtime never hardcodes table names — it reads `table_name` from `_app_objects` (`runtimeEconomySupport.ts:150-161`).

Inference: cooldown = acquire the per-user advisory lock `mining:<appId>:<userId>` inside the fire transaction (serializes the user's own fires), then one parameterized query for the user's latest `Mine` operation (`_upl_created_by = $1` + `OperationKind` column = `'Mine'` or the `Mine` OperationType value id via `resolveOperationTypeValueId`, `runtimeEconomySupport.ts:224-237`) compared against `MiningCooldownMs`. `LastMinedAt` (authored `DATE`, not required — there is **no DATETIME component type**, `metahub-authoring.ts:841-846`) remains per-asteroid state for the state endpoint/UX, not the cooldown source.

### RQ4 — Idempotency and request validation for `fire`

Facts:

- `economyTradeKindSchema = z.enum(['sell','buy'])` (`packages/universo-react-types/src/common/economyRuntime.ts:42`); `fingerprintEconomyTradeBody(kind, body)` is HMAC-SHA256 over `JSON.stringify({ kind, body: canonicalizeEconomyValue(body) })` (`runtimeEconomyService.ts:161-172`) — the kind is already bound into the fingerprint precisely so one key cannot replay across kinds.
- The store table `applications.obj_economy_idempotency` has **no `kind` column** (migration `1800000000370-CreateEconomyIdempotency.sql.ts:10-36`; columns `key_hash`, `body_fingerprint`, `response`, `status_code`, `expires_at`; `UNIQUE (application_id, user_id, key_hash)` at `:25-26`); the gate lock is `economy-idem:<appId>:<userId>:<keyHash>` acquired inside the trade transaction (`runtimeEconomyService.ts:92,212-215,602-603`); only 200 responses are stored (`:726-735`).
- A fire without an `Idempotency-Key` is allowed in trade today (key parsing is conditional, `runtimeEconomyController.ts:95-114`; malformed → 400) — the same applies to fire, protected by the cooldown + asteroid lock instead (TZ §8.3); keys are UUID v7 (`economyUuidV7Schema`, `economyRuntime.ts:8-13`).
- Request/response schemas live beside the trade schema (`economyTradeRequestSchema` `:44-51`, `economyTradeResponseSchema` `:67-74`, `economySummarySchema` `:76-103` strict) — a strict `economyMineRequestSchema` (`{ asteroidCode }` only), `economyMineResponseSchema` (FR-019 fields: `operationId`, asteroid code/remainder/status, chunks, cargo used/max, wallet echo) and a strict `economyMiningStateSchema` have no precedent blockers; the store persists arbitrary JSON responses.

Inference: extend `economyTradeKindSchema` with `'mine'`; fingerprint over `{ kind: 'mine', body: { asteroidCode } }` (same key + same asteroid → replay; same key + different asteroid → `ECONOMY_IDEMPOTENCY_CONFLICT`, matching TZ §8.3); add the strict request schema and the two response schemas in `economyRuntime.ts`. **No migration** — the table/fingerprint/lock format is reusable as-is. The strict request body is also the FR-030 mechanism: any forbidden/server-owned client field (`quantity`, `mass`, `remaining`, `cargo`, …) fails schema validation and the route rejects with 422 `MINING_INVALID_PAYLOAD` (TZ §8.2), mirroring the trade route's forbidden-body-keys 422 (`runtimeEconomyController.ts:23-28,84-86`).

### RQ5 — Client target-vs-fly semantics (decisive)

Facts:

- `SceneObjectConfig` is `{ id, role?, position, scale, selectable?, guard? }` (`playcanvasCanvasWidgetRuntime.ts:43-50`); normalization strips unknown fields (`PlayCanvasCanvasWidget.tsx:80-99`); the shared published-scene zod schema is **strict** (`packages/universo-react-types/src/common/playcanvasProjects.ts:483-492`, `.strict()` at `:492`, objects `.max(64)` at `:496`) — a `kind: 'asteroid'` tag arriving from a published manifest fails validation and the widget fails closed.
- Every non-camera sceneObject becomes a box entity with one shared material (`playcanvasCanvasWidgetRuntime.ts:337-348`); the pick loop is ray-AABB over `selectable` sceneObjects (`:424-482`, nearest hit returned as `{ objectId, point: object.position }`); `handleCanvasClick` unconditionally converts any picked objectId into a server `move_to_object` intent (`PlayCanvasCanvasWidget.tsx:554-563`); the `targetObjectId` fallback picks "first sceneObject id ≠ controlled" (**`PlayCanvasCanvasWidget.tsx:296-299`** — not the runtime file).
- Test constraints (full path: `packages/universo-react-apps-template-mui/src/dashboard/components/__tests__/PlayCanvasCanvasWidget.test.tsx`): the host-bridge test asserts **exact key equality** `['sendIntent', 'pickAt', 'getParticipants']` on `app.__universoHost` (`:2314-2317`) and rendered entity names use exact lists (`:776-778`, `:2592-2594`); there are **zero pointer-sequence or canvas-click tests** — the drag threshold (`Math.abs(dx)+Math.abs(dy) > 2`, `:534-537`) is untested, so raising it to ~6px (TZ §11.2) breaks nothing; double-click tests bypass pointer handlers entirely.
- Highlight precedent: the Visual Lab glow shell — a sibling entity with `createTranslucentStandardMaterial({ emissiveIntensity: 14, opacity, additive: true })` (`visualLinkupLabRuntime.ts:171-201`; helper `packages/universo-react-playcanvas-engine/src/runtime.ts:105-120`), shown/hidden via `entity.enabled` toggling (`:284-292`).
- The asteroid belt state comes from `GET mining/state` (server data), **not** from the published scene manifest — so no change to the strict scene schema is needed at all; asteroids render from a parallel array owned by the mining query, outside the 64-object cap and outside the runtime effect's `sceneObjects` dep array (`playcanvasCanvasWidgetRuntime.ts:1004-1034`).

Inference (minimal-risk design): render asteroids from the mining-state payload into a **parallel asteroid entity list** (this avoids all five decisive risks: the unconditional `move_to_object` conversion, the `targetObjectId` hijack, the strict schema, the exact-equality entity tests, and the dep-array teardown coupling). Add a sphere/ray branch for asteroid picking (next to `intersectAabb`, or a sibling pick function); in `handleCanvasClick`, branch on the pick result: asteroid hit → set the local mining target (React state + glow-shell `enabled` toggle), anything else → the existing `move_to_object`. Hover (FR-031): the hovered asteroid shows distance vs `MiningRadiusMeters` and marks out-of-range — the hover HUD reads the same React state, with screen positioning available from the `worldToScreen` projection markers (`playcanvasCanvasWidgetRuntime.ts:548-562`) or a React-state HUD. Fire button mirrors the MyLocation IconButton, which already shares its handler with the `Enter` key (`PlayCanvasCanvasWidget.tsx:747-758` + `:577-579`) — `F` is a new branch in `handleCanvasKeyDown` calling the same fire handler with `preventDefault()`. The button disables when there is no target, during cooldown, or while the mutation is pending. `Depleted` asteroids render darkened/hidden (FR-018) and are removed as targets; asteroid shape/color are deterministic from `code`/`visualVariant` (FR-003).

### RQ6 — `MiningConstants` resolution and state caching

Facts:

- `resolveEconomyConstants` (`runtimeEconomySupport.ts:267-290`): loads all constants via `loadApplicationRuntimeConstants` (raw SELECT over `_app_constants`, fail-soft, `applicationRuntimeConstants.ts:22-58`), finds the Set row by codename in `_app_objects`, groups by `groupId`, returns a codename-keyed Map; `resolveEconomyConfig` (`runtimeEconomyService.ts:287-334`) validates required codes and reads via `readNumberConstant`/`readStringConstant` (fail-closed).
- `_app_constants` is materialized at sync/publication by `syncSetConstants` from `snapshot.fixedValues ?? snapshot.constants` (`syncSeeding.ts:633-676`).
- The state GET reads five asteroid rows via the established raw-SQL pattern (`resolveEconomyObjectCollection` + `requireAttr` + `buildEconomyActiveCondition`, `runtimeEconomySupport.ts:145-186,308-309`).

Inference: a `MINING_CONSTANTS_SET_CODE = 'MiningConstants'` constant + a resolver mirroring `resolveEconomyConstants` verbatim (only the codename parameter changes) + a required-codes list + readers. Caching: **none for MVP** — the state endpoint reads five rows (p95 ≤ 200 ms is expected to hold at that size; verify in integration) and client polling is already gated at 2 s; the TZ §9.6 cache is optional ("можно кэшировать" — "may be cached"), add a 1–2 s in-memory map only if load profiling demands it.

### Residual findings

- **Service placement**: `postOperationRow` is a closure inside the `createRuntimeEconomyService` factory (`runtimeEconomyService.ts:388-411`) — the mining flow either colocates in the same factory (recommended: it also reuses `resolveEconomyConfig`, `createEconomyRow`, ledger ids, the idempotency gate) or re-wraps the exported `runRecordStateCommandCore` (returned by the `createRecordStateCommandHandlers` factory at `posting.ts:341`). `getEconomySummary` (`:560-589`) and `executeTrade` (`:591-743`) are the structural skeletons to clone: savepoint → gate → config → validations → `createEconomyRow` → post → fresh reads → zod parse → idempotent response save.
- **TZ §9.4 transaction shape (verbatim carrier for PLAN)**: `SELECT … FOR UPDATE` the asteroid row → **re-check remainder/status after acquiring the lock** (the TOCTOU guard the Doyensec class targets) → create the Operation → post → update `RemainingQuantityKg` **and `Status` (REF flipped to `Depleted` at zero remainder) and `LastMinedAt`** in the same transaction; the remainder `UPDATE` is schema-qualified, parameterized, with `RETURNING` + fail-closed on zero rows (AGENTS.md Mutation Rule).
- **TZ §9.3 chunk math (semantics PLAN must not reinvent)**: skew exponent `base ^ (1/ChunkMassSkew)`, round each mass to 0.1 kg, scale masses down proportionally when `total > remaining`, last chunk equals the remainder when it is below the min chunk mass, capacity rejection happens **before** any `Operation` is created (FR-016/FR-017), and `total < 0.1 → MINING_DEPLETED`. Pure, unit-testable function; tests assert ranges/sums, not fixed masses (TZ §9.3).
- **Error-code plumbing**: the client `localizeEconomyError` gates on the `ECONOMY_` prefix (`EconomyDialog.tsx:97-103`) — TZ §8.2's `MINING_*` codes would fall through to the generic message. Codes must be added to the types whitelist `economyErrorCodeSchema` + `economyErrorStatusByCode` (`economyRuntime.ts:15-40`) AND the duplicate backend map `ECONOMY_ERROR_STATUS_BY_CODE` (`runtimeEconomySupport.ts:107-117` — itself missing `ECONOMY_IDEMPOTENCY_KEY_INVALID`, a pre-existing drift), and the client prefix gate extended to accept `MINING_*` (or a parallel `localizeMiningError` + `runtime.miningErrors.*` i18n block; existing keys at `apps.json:631-644` en/ru). There is no client-side code whitelist beyond the prefix check — any whitelisted code flows automatically once the i18n key exists. The operations-list `Mine` label is already pre-wired (`EconomyDialog.tsx:31-37`, i18n `apps.json` en/ru) and needs no new component.

## Conflicts And Uncertainty

1. **TZ §8.2 code names vs the client prefix gate** — `MINING_*` codes (TZ-verbatim) require extending the `ECONOMY_`-prefix check in `localizeEconomyError` or a parallel miner-specific localizer; renaming codes to `ECONOMY_MINING_*` would reuse the gate verbatim but deviate from the TZ. Recommendation below keeps TZ names.
2. **TZ §10.2 headline vs shared-config reality** — "targetLedgers для Mine — только InventoryLedger" ("targetLedgers for Mine — InventoryLedger only") is not literally expressible (per-record config on the shared Operation entity; both-codenames contract assertion); the TZ's own fallback clause applies. Already reconciled in the brief's OQ2; the research adds the mechanism evidence (`metahub-authoring.ts:1478-1494`, `mmoommAppContentContract.ts:408-414`).
3. **Cooldown source ambiguity** — TZ §9.3's pseudocode mentions cooldown without naming the source; §9.5 fixes it per-user while §7.2's `LastMinedAt` is per-asteroid. Resolved by evidence: per-user last-Mine query under a per-user advisory lock; `LastMinedAt` is state, not the cooldown source.
4. **Line-of-sight option (TZ §9.2/§16-Q5)** — the TZ delegates the choice between "target + distance" and "target + distance + line of sight" to RESEARCH. Decision: **distance-only in MVP** — the minimal TZ check; the camera is an independent orbit (no heading coupling), all five asteroids orbit in open space near the station, and a LOS check would need station/guard-zone geometry that adds validation complexity without MVP value. If a LOS check is ever added, it is a separate `MiningConstants` parameter and must not block asteroids outside guard zones (TZ §9.2 constraint).
5. **No index on `_upl_created_by`** — the cooldown query is a seq scan on the per-app Operation table; acceptable at MVP scale, flagged for later profiling rather than premature index DDL (which the TZ forbids: no platform schema change).

## Recommended Decision

1. **`StationCode` on the Mine fact**: reuse the trade fallback — resolve the first active `FlightStation` row inside the fire transaction (`loadFirstStationRow`) and stamp `Code ?? rowId` exactly like the posting module does today. No ledger change; no new `FlightStation.Code` component in MVP (optional stakeholder upgrade later). The mining UI does not surface the stamped station in MVP.
2. **Service placement + transaction**: colocate `getMiningState`/`executeMiningFire` inside the `createRuntimeEconomyService` factory to reuse the `postOperationRow` closure, `resolveEconomyConfig`-style resolution, `createEconomyRow`, ledger ids and the idempotency gate; PLAN owns the exact file split. The fire transaction follows TZ §9.4 verbatim: `SELECT … FOR UPDATE` → **re-check remainder/status under the lock** (TOCTOU guard) → `createEconomyRow` (server-stamps `OperationKind`/`AsteroidCode`) → post → update `RemainingQuantityKg` **and `Status` (`Depleted` at zero) and `LastMinedAt`** — schema-qualified, parameterized, `RETURNING` + fail-closed.
3. **`OperationKind` branching**: author `OperationKind`/`AsteroidCode` as server-owned STRING components (additive schema sync, no migration); the posting module branches on `kind === 'Mine'` read via `ctx.records.get` (codename-keyed), keeps the legacy heuristic fallback, validates the Mine invariants, and returns only the InventoryLedger movement group; `targetLedgers` stays `[WalletLedger, InventoryLedger]`; contract edits are additive (new codenames + serverOwned assertions; enum values already contain `Mine`).
4. **Cooldown**: per-user advisory lock `mining:<appId>:<userId>` + a "latest Mine operation of the user" parameterized query (StarterGrant-query template) compared against `MiningCooldownMs`, both inside the fire transaction; `LastMinedAt` (DATE, optional) remains per-asteroid state. No new table, no index DDL for MVP (seq scan flagged).
5. **Idempotency + request validation**: `'mine'` into `economyTradeKindSchema`; strict `economyMineRequestSchema` (`{ asteroidCode }`) whose schema failure surfaces as 422 `MINING_INVALID_PAYLOAD` (FR-030); fingerprint `{ kind: 'mine', body: { asteroidCode } }`; `economyMineResponseSchema` + `economyMiningStateSchema` in types; key optional (UUID v7), no-key fire protected by cooldown + asteroid lock; no migration.
6. **Error codes**: keep TZ §8.2 `MINING_*` names verbatim; register them in both code maps (types + backend), extend the client prefix gate to `MINING_*` (or add `localizeMiningError` + `runtime.miningErrors.*` en/ru block); keep the generic fallback; optionally fix the pre-existing `ECONOMY_IDEMPOTENCY_KEY_INVALID` map drift while touching the backend map.
7. **Client targeting**: asteroids render from the `mining/state` payload into a parallel entity list (never `sceneObjects` — five decisive risks documented, dep array included); sphere-pick branch beside `intersectAabb`; `handleCanvasClick` branches asteroid hits to target selection (React state + glow-shell `enabled` toggle, Visual Lab precedent) and leaves everything else on `move_to_object`; hover shows distance/availability with out-of-range marking (FR-031); drag threshold raised to ~6px (TZ §11.2; test-safe); Fire button mirrors the MyLocation button↔`Enter` pairing with `F` in `handleCanvasKeyDown`; disabled when no target / cooldown / in-flight; `Depleted` asteroids dim/hide and are dropped as targets.
8. **Line of sight**: none in MVP — server validates target + distance only (TZ's minimal check; camera is a free orbit); a future LOS check would be a separate `MiningConstants` parameter that must not block asteroids outside guard zones.
9. **HUD & polling**: React-state HUD overlay inside the container Box (`position: 'relative'` + `pointerEvents: 'none'`); `useMiningState` hook gated on ready + realtime connected/restored + member mode with `refetchInterval: 2000` (TanStack v5 default pauses in hidden tabs — primary-source verified).
10. **Visuals**: laser = thin elongated box with additive translucent material (nose→asteroid); chunks = 1–3 low-poly sphere entities with mass-proportional scale (TZ §11.3), deterministic asteroid shape/color from `code`/`visualVariant` (FR-003); materials tracked and destroyed (lab pattern); short-lived entities destroyed mid-session via engine-standard `entity.destroy()`; `prefers-reduced-motion` support is net-new (TZ §13).
11. **State caching**: none for MVP; optional 1–2 s in-memory cache later (TZ §9.6 is permissive, not mandating).
