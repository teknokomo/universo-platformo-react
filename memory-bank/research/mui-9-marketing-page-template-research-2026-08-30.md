## Research Question

Is the reviewed task brief sufficiently complete to plan and implement an all-workspace MUI 9 migration plus a data-driven `marketing-page` template, while keeping the database disposable and avoiding schema/template version bumps? Which repository contracts, external API changes, runtime paths, seed ownership rules, and browser evidence gates must be made explicit before PLAN?

The decision under review is not whether the product direction is desirable. It is whether the direction can be implemented without silently rendering a marketing layout as a dashboard, losing `templateKey` during publication/sync, overwriting authored workspace content, or claiming MUI 9 support while v5/v7/v8 dependencies and removed APIs remain in the workspace.

## Key Findings

### 1. Executive verdict

-   **[Fact]** The brief has the right product direction: move the workspace to MUI 9, keep `dashboard` and add `marketing-page`, materialize marketing content from metahub entities, keep the database disposable, and avoid schema/template version bumps.
-   **[Fact]** The current implementation is not template-aware end to end. `templateKey` is stored in some layout/snapshot records but is not carried through the application runtime response and renderer.
-   **[Fact]** Several publication, sync and seeding helpers unconditionally normalize or inject dashboard configuration.
-   **[Fact]** The current workspace has Core v7, X v8, a direct MUI Base v5 beta, missing direct `@mui/utils` ownership for imports, and source usages of APIs removed or renamed in MUI 9.
-   **[Inference]** The brief is a sound product specification but is not yet implementation-ready. PLAN must first establish a template registry/contract and a clean ownership policy; otherwise a successful build could still produce the wrong page or overwrite user content.

### 2. MUI 9 is a coordinated migration, not a catalog-only bump

-   **[Fact]** The workspace catalog in `pnpm-workspace.yaml:61-77` declares `@mui/material`, `@mui/icons-material` and `@mui/system` at `^7.3.7`, `@mui/lab` at `^7.0.0`, and MUI X packages at `^8.27.0`. The comments still describe X as not following Material UI versioning.
-   **[Fact]** Current official pages checked on 2026-08-30 identify Material UI 9.4.0 and MUI X 9.12.0, with the coordinated v9 release dated 2026-04-08. The requested `9.x` range therefore needs an exact catalog/lockfile policy rather than an unspecified major-only promise.
-   **[Fact]** The v9 guide removes deprecated APIs and standardizes slots/`slotProps`; the official codemod can migrate the complete deprecation set, but component-specific review remains required.
-   **[Fact]** MUI v9 changes its **default bundle targets** to Chrome 117, Edge 121, Firefox 121 and Safari 17. The repository has no explicit root browserslist contract, so these targets must not be presented as the application support policy until PLAN confirms them and adds a browser gate.
-   **[Fact]** MUI System v9 removes deprecated system props from `Box`, `DialogContentText`, `Grid`, `Link`, `Stack`, `Typography` and timeline content. The official `v9.0.0/system-props` codemod is required, and the migration must scan props outside `sx` rather than only searching for removed component APIs.
-   **[Fact]** Core v9 changes observable behavior and test-environment detection: Backdrop no longer adds `aria-hidden` by default; ButtonBase keyboard clicks bubble differently; Menu/Tab keyboard and `tabindex` behavior changes; `TablePagination` formats numbers with `Intl.NumberFormat`; `TextField select` renders its label as a `div`; and jsdom/happy-dom are detected by feature/user-agent checks instead of only `NODE_ENV`. These changes require accessibility, locale and Vitest/JSDOM regression checks.
-   **[Fact]** Data Grid, Pickers and Tree View are separate X packages with their own v9 migration and license considerations. Keeping X at v8 while Core moves to v9 is not a coherent “all MUI 9” result.
-   **[Fact]** MUI X v9 technically accepts Material/System `^7.3.0` or `^9.0.0`; therefore a mixed Core/X major is not automatically a peer-resolution failure, but it does fail this repository's explicit all-MUI-9 target and leaves two migration contracts active.
-   **[Fact]** Context7 confirms the v9 TextField migration (`InputProps`, `inputProps`, `SelectProps`, `InputLabelProps`, `FormHelperTextProps` to `slotProps`) and Autocomplete `componentsProps`/legacy component props migration. Context7’s MUI X index does not yet expose complete v9 version metadata, so current direct MUI pages remain the authority for X.

### 3. Dependency and source-surface audit

-   **[Fact]** `packages/universo-react-core-frontend/package.json` directly declares `@mui/base: 5.0.0-beta.40`. `pnpm why` identifies it as the sole lockfile source of `@mui/utils@5.17.1`; the source scan found no `@mui/base` import. The likely clean migration is to remove the unused v5 dependency after a package build proves it is not needed.
-   **[Fact]** Official MUI documentation says `@mui/base` is deprecated and replaced by the standalone Base UI project. It should therefore be removed when unused; if a hidden consumer is discovered, that is a separate Base UI migration decision, not an attempt to invent an `@mui/base` v9 pin.
-   **[Fact]** `packages/universo-react-apps-template-mui` imports `@mui/utils/useEventCallback`, `useSlotProps` and `visuallyHidden` but does not own `@mui/utils` in its manifest/catalog. A v9 migration must add an explicit direct dependency or change those imports.
-   **[Fact]** `apps-template-mui/src/dashboard/theme/customizations/datePickers.ts` and `src/crud-dashboard/theme/customizations/datePickers.ts` import the type-only `@mui/x-date-pickers-pro/themeAugmentation`, but `@mui/x-date-pickers-pro` is not declared by the apps-template package. The type import still requires explicit dependency ownership (or removal with the Pro package).
-   **[Fact]** `packages/universo-react-admin-frontend/src/pages/*` imports `@mui/icons-material`, but `admin-frontend/package.json` does not declare `@mui/icons-material`. The migration must fix this direct-import ownership rather than rely on a transitive package.
-   **[Fact]** `tools/testing/frontend/renderWithProviders.tsx` imports `@mui/material` and `@mui/material/styles`, while the root `package.json` does not own MUI dependencies. Either the root testing tool must declare its dev dependencies or the helper must move behind a package that owns them; a frozen install must prove the chosen boundary.
-   **[Fact]** `packages/universo-react-profile-frontend/src/pages/Profile.jsx` imports MUI while its package manifest has no direct MUI dependency. The all-workspace rule requires dependency ownership to be corrected, not merely satisfied transitively.
-   **[Fact]** `@mui/lab` is declared in applications and metahubs packages but no source import was found. Prefer removal if it is dead; otherwise pin the v9 beta explicitly and document the beta risk.
-   **[Fact]** Emotion versions are declared as literal ranges in several manifests instead of one catalog policy. Normalize them to one compatible set during the migration or record a deliberate exception.
-   **[Fact]** `auth-frontend` peers accept `@mui/material >=7`, and `migration-guard-shared` accepts `>=5.0.0`. These ranges contradict an explicit v9-only package contract unless the packages are intentionally version-agnostic.
-   **[Historical finding, resolved]** At the initial audit the repository catalog resolved React to 18.3.1 while the lockfile contained `react-is` 16.13.1, 17.0.2, 18.3.1 and 19.2.4. Official Material UI installation guidance requires React 18-or-below projects to resolve `react-is` to the same React version. The implementation now pins the root override and lockfile to `react-is` 18.3.1; MUI v9 itself does not require React 19.
-   **[Fact]** `tools/check-catalog-versions.mjs` does not enforce MUI policy. A dedicated static gate is needed for Core/X major alignment, old v5/v7/v8 ranges, undeclared direct imports, lockfile consistency and peer ranges.

### 4. The `.backup` templates are references, not a safe replacement tree

## Conflicts And Uncertainty

-   **Brief versus runtime ownership:** The brief describes a metahub→publication→application→workspace precedence model, but `syncWorkspaceSeededElements` currently updates existing seeded rows. The precedence must be resolved before any acceptance test is called authoritative.
-   **No legacy code versus transition architecture:** The request allows a clean break because the database is disposable, while the architecture notes describe an ongoing transition and `apps-template-mui` still exports deprecated `Runtime*` aliases. PLAN must define the exact touched-path cleanup boundary; do not silently remove unrelated aliases across the repository or silently preserve them as a “compatibility” layer.
-   **Template switching semantics:** Storage accepts a generic `template_key`, but application update SQL does not update it and the UI hardcodes dashboard. The brief should not promise in-place switching unless a separate API/store operation is planned.
-   **MUI version precision:** “9.x” is underspecified. Official pages currently show Core 9.4.0 and X 9.12.0; the plan needs a coherent exact set, lockfile policy and release/upgrade cadence.
-   **React/`react-is` resolution (resolved for this slice):** The repo stays on React 18.3.1 and pins the root `react-is` override and lockfile to 18.3.1, matching the official MUI React-18 installation guidance. Future React/MUI major upgrades must revalidate this pair and the peer graph.
-   **MUI Base versus Base UI:** The direct `@mui/base` dependency appears unused and is officially deprecated. Confirm no hidden import/build plugin needs it; if one exists, decide separately whether Base UI belongs in this migration.
-   **System props and test runtime:** The current source has many system props outside `sx`, and MUI v9 explicitly changes jsdom/happy-dom detection. The residual scan and focused test rerun are mandatory, not optional cleanup.
-   **Registry documentation drift:** `memory-bank/projectbrief.md` and the architecture skill still describe only four metahub templates (and a curated table that omits current specialized entries), while source and the shape test prove seven. Source/test are authoritative for this change; the plan must decide whether to refresh those docs in scope.
-   **MUI X documentation freshness:** Context7’s X index is partly v8-oriented. Direct official MUI X v9 migration/release pages were used for current claims; future patch-level changes still require verification at implementation time.
-   **Legacy marketing ownership:** `template-mui/src/views/start-page/MarketingPage.tsx` is a separate, partially enabled legacy start surface. `techContext.md` permits intentional duplication during the transition, so the clean-break request does not by itself authorize deleting it. PLAN must state whether it remains isolated, is adapted to the shared contract, or is retired with an explicit caller migration.
-   **Code-graph freshness:** OntoIndex reported a stale index and could not submit a refresh because the worktree already contains user changes; the CLI is not installed locally. Current claims in this artifact therefore rely on direct source/tests, not graph traversal, until a clean worktree permits a refresh.
-   **Pro licensing:** The repository declares Pro package dependencies but the local source audit found no runtime Pro component or `LicenseInfo` use. It is unknown whether any package is loaded indirectly in a production path. Remove dead Pro packages or define a secret-safe environment/config injection and CI/runtime behavior before claiming a green migration.
-   **Public marketing scope:** The brief scopes the first runtime to authenticated `/a/:applicationId`, while the app also has an LMS-style public `GuestApp` route. Whether marketing should be publicly shareable is a product decision, not an implementation detail.
-   **Marketing actions:** Stock CTA, navigation and newsletter controls are visually present but inert. It is unknown whether the acceptance target is pixel/section parity only or working entity-configured navigation/actions.
-   **Media provenance:** Stock image URLs are external and unstable. The final fixture must decide between checked-in local assets, ResourceSource references, or a deterministic placeholder/fallback contract.
-   **Scoped workspace widgets:** Workspace-enabled sync currently injects dashboard widgets into every layout. The expected marketing behavior for workspace switcher/divider and scoped layout overrides needs a specific decision.
-   **Manifest validator shape:** The validator accepts arbitrary template keys while its seed widget type is dashboard-only. It is unclear whether the intended marketing layout has an explicit empty widget map or a new template-owned section map; PLAN must choose one canonical manifest shape.
-   **Browser support:** The official v9 default bundle targets are known, but the repository has no explicit browserslist policy. It is unknown whether older browsers remain supported by product requirements.
-   **Baseline evidence:** The brief requires one-to-one section and demo parity, but the prior artifact had only record counts. Exact semantic content/media/navigation keys and a screenshot provenance/golden-diff policy are needed before “one-to-one” can be a testable claim.

## Recommended Decision

Proceed to PLAN, but treat the current brief as **directionally accepted and implementation-blocked by explicit contract work**. The recommended order is:

1. **Freeze the migration contract.** Select exact Core/X/Lab/Emotion/utils versions, React/`react-is` policy, browser support (separate from MUI's default bundle targets), Pro licensing strategy, lockfile policy, direct dependency ownership for every importing package/tool, and the clean-break boundary for old aliases/legacy imports.
2. **Create one template registry.** Define `dashboard` and `marketing-page` keys, template-specific config schemas, manifest validation, and a shared discriminated runtime envelope. Reject unknown keys and invalid template/config combinations.
3. **Make publication and sync template-aware.** Preserve key/config in snapshots and `_app_layouts`; remove silent dashboard fallbacks and dashboard widget injection for marketing; fail publication loudly on invalid attachment.
4. **Resolve content ownership before implementation.** Choose initial-only seed preservation, authoritative republish, or explicit provenance/dirty state. The default recommendation is initial-only seeded demo rows plus an explicit reset-to-source action, because workspaces own authored content.
5. **Build the typed marketing data contract.** Keep the stock baseline counts/order, map stable semantic codenames to localized entity values, and return per-section data without forcing heterogeneous records into a dashboard response.
6. **Refactor rendering and theme boundaries.** Add a public marketing export and a shared hosted/standalone dispatcher. The marketing renderer should be presentational under the existing app shell and must not add a nested `ThemeProvider`/`CssBaseline`. Decide separately whether the legacy `template-mui/src/views/start-page/MarketingPage.tsx` remains isolated, consumes the shared data contract, or is retired through a caller migration.
7. **Migrate MUI APIs with proof.** Run the official Core deprecation and `v9.0.0/system-props` codemods plus package-specific X presets; then perform manual slot, Charts CSS, locale/DOM, icon, test-runtime and license review and package-level build/lint checks. Do not copy generated backup JavaScript or wholesale replace the product dashboard.
8. **Add deterministic fixture and browser gates.** Prefer a generated/tracked marketing snapshot with semantic drift normalization, a complete app-bar/hero/footer semantic manifest and approved visual-baseline provenance when pixel parity is claimed, then test create→publish→sync→runtime and export/import. Add EN/RU × light/dark and desktop/tablet/mobile UX evidence plus RBAC/direct-API/content-safety tests.
9. **Close with repository-wide validation.** Run targeted package builds/lints, the MUI policy gate, fixture drift checks, exact Playwright specs and the project’s required review gates before considering the migration complete.

This path satisfies the no-schema/template-version-bump constraint because it reuses existing snapshot/layout fields and changes validation/runtime behavior. It also preserves the project’s template-first and apps-template isolation architecture while making the hidden dashboard assumptions explicit.
