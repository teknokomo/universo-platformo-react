## Research Question

1. What is currently true in the repository about runtime workspace access (storage, membership resolution, default workspace, invitations, public/guest boundaries)?
2. Which repository decision must PLAN lock before implementation?
    - **D1**: how baseline `member` access to `shared` workspaces for all active `applications.rel_application_users` is resolved (dynamically in SQL vs. materialized rows in `_app_workspace_user_roles`);
    - **D2**: how to prevent `ensurePersonalWorkspaceForUser` from auto-creating a duplicate `Main` personal workspace after in-place conversion;
    - **D3**: who may convert `personal` → `shared` (workspace owner role vs. application `manageApplication`);
    - **D4**: membership cleanup semantics on application leave/remove once baseline rows exist.

## Key Findings

### A. Access model evidence from industry primary sources

-   **Microsoft Teams (strongest structural match)**: Standard channels are "available to all team members" by default; Private channels are visible to and joinable only by explicitly added members, and members must already be members of the team; only channel owners add members by default. This is exactly the two-tier mapping the brief encodes: Application ≙ Team, `shared` workspace ≙ Standard channel, `personal` workspace ≙ Private channel.
-   **Notion teamspaces**: Open/Closed/Private visibility lives on the teamspace, while the workspace (container) holds the member list; Default teamspaces auto-include everyone; "Notion respects the broadest level of access given to a user." The two-level ordering (container admission first, then inner-space scope) is the industry norm for the model requested.
-   **Both vendors forbid or avoid converting between types** (Teams explicitly: "You can't convert a standard channel to a private channel and vice versa"). The brief's in-place `personal` → `shared` conversion is therefore a deliberate product divergence from the Teams pattern; the mitigations are the one-way route, a confirmation dialog, and the `converted_from_user_id` traceability marker (finding F).

### B. Current storage model (verified against DDL)

-   `_app_workspaces`: `workspace_type TEXT NOT NULL DEFAULT 'personal'` (`'personal'` | `'shared'`), `personal_user_id UUID NULL`, `status`, `is_public_entry BOOLEAN NOT NULL DEFAULT false`.
-   `_app_workspace_user_roles` (`workspace_id`, `user_id`, `role_id`, `is_default_workspace`) — membership table with partial unique `(workspace_id, user_id)` for active rows (NULL-safe soft-delete state), plus per-user partial unique on `is_default_workspace = true`.
-   Partial unique on `(personal_user_id)` for `workspace_type = 'personal'` active rows → max one active personal workspace per user per schema.
-   `_app_workspaces_public_entry_ck` DB-level guard: `is_public_entry` can be true only when `workspace_type <> 'personal' AND personal_user_id IS NULL AND status = 'active'` and rows are not soft-deleted.
-   RLS is enabled only on the object/tbl tables (workspace-scoped policies keyed on `current_setting('app.current_workspace_id', true)`); the **six** workspace support tables (`_app_workspaces`, `_app_workspace_roles`, `_app_workspace_user_roles`, `_app_limits`, `_app_workspace_settings`, `_app_workspace_operation_audit`) have **no RLS**, so cross-schema membership logic in service SQL is not RLS-restricted at the workspace side.
-   The workspace DDL path is runtime DDL inside the applications-backend DDL boundary (`ensureWorkspaceSupportTables` is idempotent: `ADD COLUMN IF NOT EXISTS` etc.), so a new column (e.g. `converted_from_user_id`) does **not** require a platform migration or a schema/template version bump.

### C. Personal workspace bootstrap and the duplicate-creation trap

-   `ensurePersonalWorkspaceForUser` runs on: first runtime access (`resolveRuntimeWorkspaceAccess`, when `ensurePersonalWorkspace !== false`), public application `join`, admin `addMember`, and schema sync via `ensurePersonalWorkspacesForApplicationMembers`. It looks up `workspace_type='personal' AND personal_user_id=$1 … LIMIT 1`, else inserts with `ON CONFLICT (personal_user_id) WHERE … DO NOTHING` and materializes the `owner` membership row plus seeds when the workspace is newly created (seed template `Main` name: `createStaticVlc({en:'Main', ru:'Основное'})`, constants at `applicationWorkspaces.ts:66–67`).
-   `updateWorkspace` (service :356–423) builds `UPDATE … SET` **only** for `name`/`description`; the Zod schema (`updateWorkspaceSchema`) validates only those fields. There is **no API** today to change `workspace_type`, and no conversion marker.
-   Trap (fact inferred from code path, verified logically): after clearing `personal_user_id` on the converted row, the partial unique index no longer contains it, so the `ON CONFLICT (personal_user_id)` protection in `ensurePersonalWorkspaceForUser` silently stops covering that user; the next runtime request or member add would insert a fresh `Main` personal workspace, and `syncWorkspaceSeededElementsForAllActiveWorkspaces` (:1533–1549) would materialize a second seed copy into it. Any conversion design needs an explicit invariant (finding F) and, ideally, serialization with the ensure path.
-   Active seed rows are materialized per workspace with fresh UUID v7 rows per workspace and `_seed_source_key` remapping; user edits drop `_seed_source_owned`; reset restores only seed-owned rows. Conversion that preserves the workspace id preserves all of these relationships untouched.
-   The existing membership upsert path (`addWorkspaceMember`) does not use `ON CONFLICT` at all (pre-SELECT + in-place UPDATE, or a plain INSERT when no row exists, runtimeWorkspaceService.ts:618–687) — the only `ON CONFLICT … DO NOTHING` precedent in workspace code is the `ensurePersonalWorkspaceForUser` INSERT (`applicationWorkspaces.ts:1681–1683`). New baseline materialization should therefore use one set-based `INSERT … SELECT … ON CONFLICT (workspace_id, user_id) WHERE _upl_deleted = false AND _app_deleted = false DO NOTHING`, a pattern PostgreSQL 17 documents as valid arbiter inference against a partial unique index (`sql-insert.html`).

### D. Current membership semantics — the "shared workspaces are invisible to uninvited members" defect

-   `listUserWorkspaces` and `getUserWorkspace` join `_app_workspace_user_roles` with `WHERE … ({wur.id IS NOT NULL} OR $N::boolean)` for admins only (`allowUnassigned`), and `resolveRuntimeWorkspaceAccess` builds `allowedWorkspaceIds` from the same membership rows. A plain application member therefore never sees a `shared` workspace in the switcher/list/runtime without an explicit invite — while `createSharedWorkspace` writes only the creator's owner row. This is the primary gap the two-tier model must fix; it also matches the defect framing in brief v2.
-   `setDefaultWorkspace` fails closed with `USER_NOT_MEMBER` when the caller has no row, and `getWorkspaceMembership` (owner checks for `requireOwner` endpoints) is membership-row-based. Both work unchanged **only if** baseline member rows exist for every application member in every shared workspace → strong evidence for the materialized model (finding E).
-   Record-level access entries (access-config capability with `principalType='workspaceMember'`) validate principals against an **explicit active row** in `_app_workspace_user_roles` (`runtimeRowSupport/access.ts:690–703`). A dynamic-only visibility model would silently break seeded/created access entries for all but explicit owners. This is the decisive argument for materialization.
-   Existing UI member surfaces (`listWorkspaceMembers` rendering the Access tab, `canRemove`, last-owner guard `LAST_WORKSPACE_OWNER_REMOVAL_BLOCKED`) assume row-based membership; they display correct results under materialization.
-   **Cross-schema membership SQL is precedented**: `listWorkspaceMembers` already joins `auth.users` and `profiles.obj_profiles` from the runtime schema service (runtimeWorkspaceService.ts:865–866); `applications.rel_application_users` RLS `readMemberships` permits reads when the reader holds an active membership row in the same application (`platform/migrations/1800000000000-CreateApplicationsSchema.sql.ts:774–783`). So both a set-based `INSERT … SELECT` materialization and a runtime `EXISTS` join are RLS/viability-safe.
-   Personal workspaces already accept owner invitations today (tests pin it: `runtimeWorkspaceService.test.ts:630–673` "allows owners to invite members into a personal workspace", `runtimeWorkspaceController.test.ts:540–587`). The clarified two-tier model keeps this behavior; the earlier v1 brief wording "block invitations into personal workspaces" is superseded — no blocking change is required, only documentation and the new shared-baseline visibility.

### E. Materialized baseline membership for shared workspaces (RECOMMENDED for D1)

-   Mechanism: on (1) `createSharedWorkspace`, (2) conversion `personal` → `shared`, (3) application `join`/admin `addMember`/sync pass, insert idempotent baseline rows (`role = workspace 'member'`, `is_default_workspace = false`) for every active `applications.rel_application_users` member of the application into every active non-personal workspace: `ON CONFLICT (workspace_id, user_id) WHERE _upl_deleted = false AND _app_deleted = false DO NOTHING` (pattern already used at `applicationWorkspaces.ts:1681–1683`; PostgreSQL 17 `sql-insert.html` confirms arbiter inference on partial unique indexes). On `leave`/`removeMember`, soft-delete the departing user's role='member' rows in shared workspaces.
-   Extra evidence for D1 (QA addendum): the `WorkspaceSwitcher` switch mutation calls `updateDefaultRuntimeWorkspace` (PATCH `…/runtime/workspaces/:workspaceId/default`, `apps-template-mui/src/dashboard/components/WorkspaceSwitcher.tsx:95–122`, API client `workspaces.ts:269–282`), which maps to `setDefaultWorkspace` → `USER_NOT_MEMBER` when the caller holds no row. Under the visible-to-all model the switcher must therefore be backed by materialized rows, or default switching breaks exactly for the workspaces it newly exposes.
-   Costs/limits: row growth is bounded by members × shared workspaces, which are curated/admin-created objects; the partial unique index makes reruns safe; one set-based SQL statement covers the sync path (loop only personal-seed materialization exists today, so per-workspace loops are acceptable precedent).
-   Alternative (dynamic `EXISTS` against `applications.rel_application_users`) was evaluated and **not recommended**: it requires touching `listUserWorkspaces`, `getUserWorkspace`, `getWorkspaceMembership`, `setDefaultWorkspace`, `resolveRuntimeWorkspaceAccess`, realtime `allowedWorkspaceIds`, record-access principal validation, and members-listing semantics, and it still needs per-user rows for `is_default_workspace`. Materialization keeps every existing membership-dependent path working unchanged and preserves fail-closed behavior.

### F. Race-safe conversion invariant (RECOMMENDED for D2)

-   Add `converted_from_user_id UUID NULL` to `_app_workspaces` (idempotent `ADD COLUMN IF NOT EXISTS` in `ensureWorkspaceSupportTables` + optional partial unique index on `(converted_from_user_id)` for active rows to hard-cap one conversion per user per schema).
-   Conversion transaction: lock the personal workspace row `FOR UPDATE` (optionally under the same `advisory XactLock` family used by `setPublicEntryWorkspace`/`enforceObjectWorkspaceLimit`), then in one `UPDATE`: `workspace_type = 'shared'`, `personal_user_id = NULL`, `converted_from_user_id = <owner>`, bump `_upl_version`. Simultaneously materialize baseline member rows (point 3 of finding E).
-   `ensurePersonalWorkspaceForUser` gains one extra existence check alongside the personal lookup: a workspace with `converted_from_user_id = $1` (active) ⇒ do not create a personal workspace. This keeps the ensure path single-user-correct under concurrency with the conversion transaction.
-   Optional: extend the `_app_workspace_operation_audit` CHECK (`operation_kind IN ('seed_reset')`, DDL :222–224) with `'personal_to_shared_conversion'` and write one audit row inside the same transaction; this is additive, idempotent-rerunnable DDL in the same file.

### G. Conversion authorization (D3)

-   Owner-only is the minimal-surprise rule: the `personal` workspace row is created with the owner's role 'owner' membership in `_app_workspace_user_roles`, the UI's owner-gated menu (`canManageWorkspace = roleCodename === 'owner'`, RuntimeWorkspacesPage :706) matches, and only the owner's own data visibility is affected. No `manageApplication` requirement is strictly needed.
-   Application admins (`manageApplication`, roles `owner`/`admin`) currently cannot edit/delete/copy/manage-members of workspaces where they hold no row (plain `requireWorkspaceMembership` with `requireOwner`); only settings/get/list/reset have admin-aware paths. Granting admins conversion rights would require a new access branch; the brief leaves this open. Notion/Teams precedent: private→open type changes are performed by the space owner, not by arbitrary admins (Teams: only shared-channel owners add members; Notion: teamspace owners change visibility).
-   The user's TZ wording ("для владельца или другого уполномоченного пользователя") supports at least owner; PLAN must decide whether to include an admin path in v1.

### H. Public/guest boundary stays unchanged (verified fail-closed)

-   All anonymous paths filter `workspace_type <> 'personal' AND personal_user_id IS NULL` (publicRuntimeAccess helpers, access-link resolution loop, eligible-quiz listing, `/l/<slug>` availability): a converted workspace automatically becomes eligible for guest `AccessLinks` links with no changes to those queries.
-   `resolvePublicEntryWorkspace`/`setPublicEntryWorkspace` remain explicit, server-owned, and active-non-personal-only; conversion does **not** touch `is_public_entry`; UI filter `usePublicEntryWorkspaceSettings.ts:44–45` will start offering the converted workspace `(workspaceType !== 'personal' && personalUserId == null && status === 'active')`.
-   Anonymous access additionally requires `application.isPublic = true` (fail-closed `resolvePublicRuntimeSchema`), and `join` is allowed only for public apps (:834–836) — the Open/Closed primary tier is already application-owned.
-   Tests pinning these fail-closed behaviors: `publicApplicationsAccessLinks.test.ts:822–837` ("does not resolve public access links from personal workspaces"), `publicRuntimeAccess.test.ts:36–77`, `applicationWorkspaces.test.ts:296–298` (no automatic shared workspace at bootstrap; still true).

### I. Lifecycle cleanup gap on leave/remove (D4)

-   Today `leave`/`removeMember` (applicationsController.ts:902–917, :1310–1325) delete the `applications.rel_application_users` row and archive only `archivePersonalWorkspaceForUser`; membership rows in other user's `personal` workspaces and in `shared` workspaces are **not** cleaned (verified: `archivePersonalWorkspaceForUser` touches only `workspace_type='personal'` rows, :1772–1841). Stale rows are inert (runtime first enforces application access via `ensureApplicationAccess`), but under the materialized model they must be considered: PLAN should soft-delete role='member' rows in shared workspaces on leave/remove and decide the policy when the departing user is the **last owner** of a shared workspace (`LAST_WORKSPACE_OWNER_REMOVAL_BLOCKED` semantics exists for in-workspace removal; application-level removal currently has no such guard).
-   `assertNotOwner` blocks the application owner from leaving (`leave`:895) and from being modified/removed (`updateMember`:1223, `removeMember`:1303).

## Conflicts And Uncertainty

-   **Private→open conversion divergence**: Microsoft Teams explicitly forbids channel-type conversion; Notion documentation doesn't offer a conversion flow (visibility mode of teamspaces is a setting, but teamspaces don't have personal-owner semantics like our `personal_user_id` row). Our requirement is one-way and marker-logged; the risk (data visibility widening for previously private data) is mitigated by the confirmation dialog and cannot be trivially reversed — PLAN must present the one-way nature explicitly in the UI and docs rather than treating it as a normal in-place edit.
-   **Baseline-membership scale**: with very large member counts and many shared workspaces the materialized rows grow O(members × workspaces). The codebase routinely does per-workspace loop seed materialization, so this is consistent with existing cost patterns, but the row-count bound is a modeling limit worth recording (no hard cap exists today on member count).
-   **Authoritativeness of the clarifying TZ**: `personal` invitations are explicitly confirmed by the user's clarification and are also what current code/tests do; the research treats this as settled product intent rather than an open question.
-   **Admin conversion path (D3)**: existing controller path branches and industry precedent support owner-only, but the stakeholder's wording leaves room for an admin variant; flagged for PLAN decision, not settled here.
-   **QA resolution of the `workspaceOpenBehavior` interplay (2026-10-15 independent fact-check pass)**: the `last-used | default-workspace` application setting is **declared but not wired** — the enum and UI exist (`unifiedSettings.ts:59, :81, :248–256`; `applicationsController.ts:175`; `SettingsPanels.tsx:539–571`; dialog defaults `dialogSettings.ts:31`), but no consumer anywhere (ApplicationRuntime, runtime bootstrap, template packages) reads it to decide which workspace opens; entry resolution always comes from `resolveRuntimeWorkspaceAccess` (the `is_default_workspace` row, else first membership). The conversion implementation must therefore not couple to this setting; wiring `last-used` is a separate future task. This closes the earlier uncertainty.
-   **QA fact-check of this artifact**: an independent read-only reviewer verified 41 claims against the current worktree and test files; all structural pins (line numbers, test names, Zod fields, SQL predicates, i18n key parity) were CONFIRMED, and three wording/precision issues were corrected in place (`addWorkspaceMember` upsert is pre-SELECT + plain INSERT, not `ON CONFLICT`; "six" support tables; server-owned ordering reference moved to `runtimeWorkspaceService.ts:197`).

## Recommended Decision

1. **D1 — materialized baseline membership** in `_app_workspace_user_roles` for all active application members of every active `shared` workspace (idempotent `ON CONFLICT DO NOTHING`), maintained at create/convert/join/addMember/sync, with role='member' row cleanup on leave/removeMember. Justified by the explicit-row dependency of record-level access entries (:690–703), `setDefaultWorkspace`, members-list UI, and realtime `allowedWorkspaceIds`; keeps all existing membership code paths correct.
2. **D2 — `converted_from_user_id` marker** on `_app_workspaces` (idempotent DDL, optional partial unique), row-locked conversion UPDATE, and a corresponding check inside `ensurePersonalWorkspaceForUser`; optionally one audit row in `_app_workspace_operation_audit` (extend the CHECK). Prevents duplicate `Main` after conversion; preserves `ON CONFLICT (personal_user_id)` for the never-converted majority.
3. **D3 — owner-role-only conversion for v1** (workspace's own owner). Expose `convert personal → shared` to authorized application administrators only as an explicit extension, if PLAN decides the admin path is needed; do not silently grant admins access to members' personal workspaces without an explicit rule.
4. **D4 — minimal leave/remove cleanup**: soft-delete the departing user's role='member' rows in shared workspaces; leave `owner` rows intact (inert but preserving audit trail) and surface the last-owner edge in PLAN rather than inventing auto-transfer UX in this batch.

## Open Questions Before PLAN (with proposed best-practice resolutions)

All questions below now carry a research-level recommendation; PLAN may ratify or adjust them, but none remains unbounded.

-   **Q1 — no-duplicate guard design: marker-only vs. any-membership.**
    _Proposed resolution_: **`converted_from_user_id` marker only**, not "any active membership". Rationale: marker semantics are exact (one conversion per user per schema, enforceable by an optional partial unique index on `(converted_from_user_id)`), restore-free (the marker is written in the same UPDATE transaction that clears `personal_user_id`), and it leaves the behavior for users who were _invited into someone else's personal workspace before ever opening runtime_ unchanged (they still get their own `Main` on first access today — changing that would be an unrelated behavioral regression).
    _Race safety_: serialize the conversion and the personal-workspace bootstrap with the repo's existing transaction-scoped advisory-lock family (`acquireAdvisoryXactLock`, already used by `setPublicEntryWorkspace` and `enforceObjectWorkspaceLimit`) keyed per user+schema, and re-check both the personal-row lookup and the marker row inside the lock before INSERT. Without this, two connections could race (ensure INSERT after conversion commit would not be blocked by the now-null `personal_user_id` arbiter).
-   **Q2 — baseline insertion: synchronous in the membership transaction vs. deferred pass.**
    _Proposed resolution_: **synchronous, inside the same DB transaction** that creates/converts the shared workspace or adds the member (mirroring how `ensurePersonalWorkspaceForUser` already runs inside the `join`/`addMember` and `leave`/`removeMember` transactions at `applicationsController.ts:846–874, :1164–1193, :902–917, :1310–1325`). It keeps fail-closed mutation semantics (no partial state if the transaction fails), matches the project's mutation rule (zero-row writes must fail closed rather than silently succeed), and is cheap: one set-based `INSERT … SELECT … ON CONFLICT … DO NOTHING` statement. When no shared workspaces exist yet the statement is a no-op.
-   **Q3 — `workspaceOpenBehavior` interplay.**
    _Proposed resolution_: **no coupling; treat as out of scope.** QA established the setting is declared-but-unwired (entity/UI only, zero consumers at entry). `resolveRuntimeWorkspaceAccess` default resolution semantics remain unchanged in this batch; wiring `last-used` (and honoring `…?workspaceId=` selection order) is a separate future task and should not block or shape conversion.
-   **Q4 — conversion error codes and DTO surface.**
    _Proposed resolution_: extend `RUNTIME_WORKSPACE_ERROR_CODES` with one dedicated code, e.g. `workspaceConversionBlocked` → HTTP 409 `WORKSPACE_CONVERSION_BLOCKED` (target workspace is not an active personal workspace of the caller), reusing existing codes otherwise: `workspaceNotFound` (404), `WORKSPACE_OWNER_REQUIRED` (403) for the owner-role gate, `WORKSPACE_ACCESS_DENIED` (403) for non-members — consistent with the existing error-code/error-mapping style in `runtimeWorkspaceController.ts` (`personalWorkspaceMutationBlocked` :142–145 precedent). Do **not** expose `convertedFromUserId` in the frontend `RuntimeWorkspace` DTO: the conversion is a client-triggered action whose state is already derivable (`workspaceType` + role), and keeping the marker server-owned matches the repo's hidden-system-fields UI rule (`mui-runtime-ux-patterns`). UI contract: one new menu item ("Convert to shared") visible only for workspace-type `personal` + `roleCodename === 'owner'`, opening a StandardDialog-confirmation (MUI 9 `aria-labelledby`/`aria-describedby`, no resize/fullscreen handles) whose localized EN/RU copy states that all application members will see the workspace with baseline member rights, that guest links become eligible when configured, that anonymous public browsing is NOT enabled automatically, that the conversion is one-way, and that IDs/records/relations are preserved.
-   **Q5 — `_app_workspace_operation_audit` extension.**
    _Proposed resolution_: **include in scope.** Extend the CHECK to `operation_kind IN ('seed_reset', 'personal_to_shared_conversion')`, write one audit row inside the conversion transaction (`affected_rows` = number of baseline member rows inserted, `actor_user_id` = converter, `source_key` = converted workspace id or the vesting marker). Rationale: irreversible visibility-scope changes deserve auditability (OWASP multi-tenant guidance includes audit/monitoring of tenant-context changes), the DDL edit is idempotent (`DROP CONSTRAINT IF EXISTS` + re-ADD pattern already used in `ensureWorkspaceSupportTables`), and the operational-audit table exists precisely for this class of event. If PLAN wants to trim, the marker column alone preserves correctness — but then the audit trail must come from SQL logs instead, which is weaker.
