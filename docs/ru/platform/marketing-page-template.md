# Шаблон маркетинговой страницы

Шаблон `marketing-page` — это лендинг опубликованного приложения на базе изолированного пакета `@universo-react/apps-template-mui` и MUI 9. Он сохраняет композицию примера MUI Marketing Page, а редакционный контент получает из записей Сущностей метахаба через зарегистрированные привязки виджетов.

![Опубликованный runtime marketing-page из seed-метахаба](../.gitbook/assets/marketing-page/marketing-page-runtime-ru-light.png)

## Создание метахаба

1. Откройте **Метахабы → Создать**.
2. Выберите **Маркетинговая страница** в локализованном выборе шаблона.
3. Оставьте включёнными стандартные пресеты Хаб, Объект, Страница, Набор и Перечисление.
4. Создайте метахаб, опубликуйте готовую версию и создайте приложение на основе этой публикации.

Seed — это начальное содержимое. Записи можно менять и расширять обычными средствами авторинга Сущностей и макета. Отдельный тип Сущности для Marketing Page не добавляется.

## Модель сущностей и композиция виджетов seed

Метахаб владеет каноническим контентом, размещениями виджетов и их привязками к источникам. В приложении доступны только зарегистрированные настройки представления и разрешённые изменения порядка, активности и размещения унаследованных виджетов.

| Объект                        | Контент                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| `MarketingPageSiteSettings`   | Общий бренд, медиа бренда, текст подвала, рассылки и юридические сведения            |
| `MarketingPageSection`        | Локализованные заголовок и описание секции                                           |
| `MarketingPageHero`           | Локализованные тексты первого экрана, подписи и типизированные действия              |
| `MarketingPageImage`          | Медиа ResourceSource, локальный альтернативный текст, декоративный признак и размеры |
| `MarketingPageNavigation`     | Упорядоченные подписи и цели навигации                                               |
| `MarketingPageLogo`           | Медиа логотипа, локализованный альтернативный текст, порядок и видимость             |
| `MarketingPageFeature`        | Заголовок, описание, иконка, превью-медиа, порядок и видимость                       |
| `MarketingPageTestimonial`    | Локализованная цитата, автор, должность, аватар или логотип, порядок и видимость     |
| `MarketingPageHighlight`      | Локализованный текст преимущества, иконка или медиа, порядок и видимость             |
| `MarketingPagePricing`        | Локализованные сведения о тарифе, цене, CTA, порядке и видимости                     |
| `MarketingPagePricingBenefit` | Локализованное преимущество и REF-связь с тарифом                                    |
| `MarketingPageFaq`            | Локализованные вопрос и ответ, порядок и видимость                                   |
| `MarketingPageFooterLink`     | Сгруппированные подписи и цели ссылок подвала, порядок и видимость                   |

Локализованные значения, семантическая идентичность, порядок и видимость принадлежат записям Сущностей. Интерфейс показывает локализованные подписи и поля; UUID, JSON привязок и физические столбцы Компонентов не выводятся как обычные значения.

## Свежий макет: 14 размещений

Новый макет содержит 14 сохранённых размещений в трёх зонах. Одиннадцать размещений привязаны к Сущностям. Аутентификация, переключатели языка и цветовой схемы — возможности хоста без редакционного источника.

| Зона               | Размещение                            | Источник                                                                   |
| ------------------ | ------------------------------------- | -------------------------------------------------------------------------- |
| `marketing-header` | `marketing.brand`                     | Семантическая запись `MarketingPageSiteSettings`                           |
| `marketing-header` | `marketing.navigation`                | Упорядоченный набор записей `MarketingPageNavigation`                      |
| `marketing-header` | `marketing.auth`                      | Действия аутентификации хоста                                              |
| `marketing-header` | `languageSwitcher`                    | Контрол языка хоста                                                        |
| `marketing-header` | `colorModeSwitcher`                   | Контрол темы хоста                                                         |
| `marketing-main`   | `marketing.hero`                      | Одна семантическая запись `MarketingPageHero`                              |
| `marketing-main`   | `marketing.image`                     | Одна семантическая запись `MarketingPageImage`                             |
| `marketing-main`   | `marketing.collection` — логотипы     | Запись секции и набор `MarketingPageLogo`                                  |
| `marketing-main`   | `marketing.collection` — возможности  | Запись секции и набор `MarketingPageFeature`                               |
| `marketing-main`   | `marketing.collection` — отзывы       | Запись секции и набор `MarketingPageTestimonial`                           |
| `marketing-main`   | `marketing.collection` — преимущества | Запись секции и набор `MarketingPageHighlight`                             |
| `marketing-main`   | `marketing.pricing`                   | Запись секции, набор `MarketingPagePricing` и связанные преимущества       |
| `marketing-main`   | `marketing.collection` — FAQ          | Запись секции и набор `MarketingPageFaq`                                   |
| `marketing-footer` | `marketing.footer`                    | Общая запись `MarketingPageSiteSettings` и набор `MarketingPageFooterLink` |

Зона `marketing-header` отображает одну адаптивную шапку и одну мобильную выдвижную панель. Дочерние размещения шапки выводят содержимое внутри общей оболочки и не создают дополнительные фиксированные панели или выдвижные меню. Порядок, активность и размещение в группах Начало/Конец определяют композицию.

В авторинге метахаба и приложения у зоны шапки есть **Настройки**. Параметр **Поведение шапки** поддерживает закреплённый режим и обычный поток страницы. Для scoped-настроек хранится только локальное переопределение; сброс настройки зоны снова показывает актуальное значение источника. Общие переключатели языка и цветовой схемы также доступны в верхней зоне Dashboard.

## Безопасный выбор источников и правила контента

Реестр поддерживает три ограниченных вида селекторов:

-   `semantic-key` выбирает одну запись по зарегистрированному семантическому Компоненту и ключу;
-   `record-set` выбирает совместимый источник-Сущность, а записи сортируются и фильтруются по зарегистрированным Компонентам;
-   `relation-set` выбирает дочерние записи по зарегистрированной REF-связи с источником родительского слота.

Каждый обязательный слот текущего Marketing размещения выбирает ровно одну цель-источник. Клиент не может передавать SQL, произвольные фильтры, физические имена таблиц и столбцов, UUID строк или собственную проекцию Компонентов. Сервер выводит и проверяет проекцию по определению виджета. В интерфейсе показываются локализованные понятные названия.

Порядком и видимостью управляют зарегистрированные компоненты записей. Параметр виджета `maxItems` может уменьшить число отображаемых записей, но не увеличить жёсткий предел реестра и resolver. Изменение порядка записей выполняется в обычном редакторе Сущностей.

Преимущества тарифа связаны с тарифом REF-компонентом `TierRef`, который хранит идентификатор записи тарифа. Resolver следует этой REF-связи; `TierKey` не является вторым ключом связи и не используется как запасной вариант.

В демо seed создаёт шесть логотипов, три возможности, шесть отзывов, шесть преимуществ, три тарифа с 4/6/4 преимуществами и четыре записи FAQ. Также создаются одна запись Hero и одна запись Image; зарегистрированные слоты допускают подключение дополнительных записей.

## Добавление, изменение и дублирование в метахабе

Реестр задаёт доступные операции для каждого размещения.

-   **Hero и Image:** Add создаёт или выбирает одну совместимую запись контента. Duplicate копирует привязанную запись и создаёт новое размещение в одной серверной транзакции: копию можно редактировать независимо, а сбой размещения не оставит осиротевшую запись.
-   **Navigation, коллекции, Pricing и Footer:** Add выбирает совместимый источник для обязательных слотов. Duplicate повторно использует привязки и не копирует строки коллекций, тарифы, преимущества или ссылки подвала.
-   **Отдельная модель источника:** после выбора совместимого источника для слота автор может создать новый пустой Объект с зарегистрированными Компонентами. Записи не копируются; для слота-связи REF указывает на выбранный родительский Объект. Записи добавляются обычным редактором Сущностей.
-   **Brand:** начальная единичная запись редактируется разрешёнными средствами авторинга; её размещение не дублируется.
-   **Возможности хоста:** аутентификация не имеет контента в Сущностях. Переключатели языка и цветовой схемы подчиняются возможностям общего реестра виджетов.
-   **Записи контента:** отдельные строки, порядок, видимость и REF-значения редактируются в обычном списке и форме записей Сущности. Диалог привязки семантической записи может также предоставить зарегистрированное действие создания или изменения выбранной записи.

Для Pricing слот `section` содержит текст заголовка, `tiers` выбирает источник тарифов, а `benefits` — это `relation-set` с родителем `tiers`. При смене родительского источника дочерняя связь должна оставаться совместимой до сохранения макета.

Права на макет, привязки и записи Сущностей проверяются сервером; видимость кнопки не выдаёт доступ. Перед записью сервер проверяет актуальный реестр и версию макета. Удаление размещения не удаляет его записи Сущностей. Запись, используемую активной привязкой, нельзя удалить или изменить её защищённый семантический ключ, пока привязка не переназначена или не удалена.

Подписи авторинга, источников и записей, проверка полей, пустые и загрузочные состояния, конфликты и ошибки прав локализованы на английский и русский языки. Политика слота задаёт обязательные локали; проверка снимка Marketing требует английский и русский тексты для локализованных полей.

Перед публикацией, импортом, восстановлением, активацией или синхронизацией снимок Marketing проверяет значения выбранных записей по контракту Компонентов. Обязательные локализованные поля должны содержать английский и русский тексты, медиа и действия проходят проверку зарегистрированных безопасных форматов, а дочерние записи relation-set должны ссылаться на выбранные родительские записи.

## Изменение и повторная публикация контента Сущностей

Чтобы обновить контент уже связанного приложения:

1. Сохраните запись Сущности и изменения макета метахаба.
2. Опубликуйте новую готовую версию публикации метахаба.
3. В уже связанном приложении синхронизируйте коннектор, чтобы импортировать опубликованные схему, контент и исходный макет.
4. Обновите runtime приложения и проверьте нужную локаль.

Настройки приложения меняют только представление и размещение. Для изменённого виджета с доступным baseline редактор показывает Reset to source: действие восстанавливает представление и параметры размещения, сохраняя привязку. Сброс настройки зоны шапки доступен отдельно. Для получения обновлений не создавайте новое приложение: публикуйте и синхронизируйте уже связанное.

## Рантайм и настройки приложения

Макеты приложения могут менять зарегистрированные параметры представления и разрешённые состояния активности, порядка и размещения унаследованных виджетов. Они не владеют контентом Marketing-Сущностей или привязками источников. Add и Duplicate скрыты для размещений Marketing из источника, а API отклоняет попытки добавить или дублировать их без доверенной привязки Метахаба. Обычные изменения конфигурации renderer не заменяют привязку.

Scoped-оверлей Marketing наследует привязку базового плейсмента; границы авторинга и snapshot отклоняют её изменение в оверлее. Если исходный макет с обязательными привязками к Сущностям удалён, его нельзя копировать во владение приложения. Сохранение локальных изменений сохраняет lineage, но атомарно деактивирует макет и помещает зависимые виджеты в tombstone; явный пропуск удаления сохраняет текущее состояние приложения.

Авторизованный runtime разрешает записи в текущей области приложения/workspace. Публичный runtime использует отдельный загрузчик готовых опубликованных данных. Оба пути применяют общие правила селекторов и строгую проверку Marketing DTO. Публичный DTO содержит только разрешённый локализованный контент и безопасные проекции медиа; в нём нет физических идентификаторов записей и Компонентов, оболочек привязок, метаданных таблиц или произвольных данных Сущностей. Изолированный MUI renderer получает проверенную модель `data.records` и не обращается к persistence.

Типизированные настройки `marketing-page` поддерживают системный, светлый и тёмный режим, необязательные цвета primary/accent и политику действий и ссылок. Название и медиа бренда поступают из привязанной записи Сущности `MarketingPageSiteSettings`. Hosted-оболочка выбирает renderer до инициализации CRUD Dashboard, владеет `AppMainLayout` и ThemeProvider и применяет настройки внешнего вида. Renderer маркетинговой страницы остаётся презентационным и изолированным от backend, authoring и database-пакетов; provider для прямого предпросмотра принадлежит standalone-оболочке.

Scoped-макет приложения для цели Page/Object может выбрать Dashboard, даже если глобальный макет использует `marketing-page`. Effective layout разрешается с учётом target до выбора renderer. Отсутствующая или неверная scoped-композиция возвращает типизированную ошибку вместо незаметного перехода к глобальному Marketing layout.

## Действия и медиа

Действия типизированы как внутренний путь, именованный якорь, внешний HTTP(S)-URL, email или телефон. Отклоняются placeholder `#`, `javascript:`, `data:`, protocol-relative URL, URL с учётными данными и произвольные endpoint. Для внешних ссылок в новой вкладке задаются `noopener noreferrer`.

Изображения и другие медиа хранятся в ResourceSource-компонентах Сущностей. Runtime формирует разрешённую проекцию; анонимный публичный вывод содержит только пригодный для публикации URL и не раскрывает адреса хранения. Отсутствующее или заблокированное медиа заменяется локализованным сообщением без показа сырого URL или объекта.

Для `MarketingPageImage`, если `Decorative` выключен, альтернативный текст обязателен на английском и русском языках. У декоративного изображения альтернативный текст может быть пустым; одинаковое правило проверяют форма, API записей, binding и импорт snapshot.

Seed рассылки использует существующее действие регистрации. API хранения лидов не добавляется: опубликованный runtime показывает CTA-ссылку и не отображает поле email, пока хост не предоставит утверждённую возможность отправки.

## Проверка

Канонический набор unit-проверок охватывает общий контракт, редактор метахаба, persistence/runtime и изолированный renderer:

```bash
pnpm run test:marketing-widget-unit-gate
pnpm check:apps-template-isolation
pnpm run test:e2e:marketing-page:verify:local-supabase
pnpm run docs:marketing-page:verify:local-supabase
```

Lifecycle- и браузерные сценарии описаны в руководстве [Браузерное E2E-тестирование](../guides/browser-e2e-testing.md). Команды Local Supabase проверяют seed, авторинг, публикацию и синхронизацию, а также runtime. `pnpm docs:marketing-page:screenshot:check` проверяет provenance и метаданные скриншотов.

## Лимит опубликованных строк

Для каждого маркетингового объекта действует предел 1000 активных строк `PUBLIC_MARKETING_ROW_LIMIT`. Публичный runtime прекращает обработку при превышении лимита. Seed и runtime-операции создания, копирования и восстановления отклоняют запись с `MARKETING_ROW_LIMIT_REACHED` при достижении предела, чтобы опубликованная страница оставалась доступной.
