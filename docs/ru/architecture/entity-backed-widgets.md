# Виджеты на основе Сущностей

Виджеты формируют макет и показывают только те параметры представления, которые зарегистрированы для соответствующего типа. Виджеты с контентом получают его из обычных записей Сущностей платформы — обычно из Объектов с Компонентами. Контракт не добавляет отдельное хранилище конструктора страниц или новый тип Сущности.

![Опубликованный runtime marketing-page с контентом виджетов из Сущностей](../.gitbook/assets/marketing-page/marketing-page-runtime-ru-light.png)

## Владение данными

| Уровень                            | Владеет                                                                                                         | Не владеет                                                     |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Метахаб                            | Схемами и записями Сущностей, каноническими seed-данными, исходными размещениями виджетов и выборами привязок   | Переопределениями представления конкретного приложения         |
| Панель приложения                  | Зарегистрированными настройками представления и разрешёнными переопределениями активности, порядка и размещения | Контентом метахаба, выбором источника и идентичностью привязки |
| Runtime опубликованного приложения | Проверенной ограниченной проекцией разрешённых записей Сущностей                                                | Авторингом или произвольным доступом к таблицам Сущностей      |
| Workspace                          | Контентом, создаваемым в runtime, только если функция явно задаёт такой жизненный цикл                          | Копией контента маркетинговой страницы из источника            |

Реестр виджетов задаёт межпакетный контракт. Определения объявляют совместимые шаблоны и зоны, слоты привязок, кардинальность источников и результатов, требования к возможностям Сущностей и семантике Компонентов, роли сортировки и видимости, политики записей, разрешённые действия авторинга и поля представления. Эти декларативные определения слотов отделены от экземпляра привязки конкретного размещения.

Конфигурация renderer хранит параметры представления. Версионируемая оболочка привязок хранится в зарезервированных нейтральных метаданных макета (<code>\_\_layout.bindings</code>), а не в контенте renderer. При материализации приложения доверенная оболочка источника сохраняется отдельно от локального состояния представления.

## Безопасные селекторы

Привязки используют строгий discriminated union из трёх видов селекторов:

| Селектор                  | Значение                                                                             | Форма сохранённого селектора                                         |
| ------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| <code>semantic-key</code> | Выбрать одну запись по зарегистрированному семантическому Компоненту и значению      | <code>{"kind":"semantic-key","field":"key","value":"default"}</code> |
| <code>record-set</code>   | Выбрать ограниченный набор записей из одного совместимого источника-Сущности         | <code>{"kind":"record-set"}</code>                                   |
| <code>relation-set</code> | Выбрать ограниченный набор дочерних записей, связанных с источником из другого слота | <code>{"kind":"relation-set","parentSlot":"tiers"}</code>            |

Цель привязки указывает тип Сущности и семантический codename. Её проекция должна соответствовать Компонентам, объявленным в реестре слота. Клиент не может передавать SQL, физические имена таблиц или столбцов, UUID строк, произвольные фильтры, предикаты связей, правила сортировки или видимости либо проекцию, созданную renderer. В интерфейсе авторинга показываются локализованные названия источников и записей, а не JSON привязок и идентификаторы хранения.

Совместимость проверяется по обязательным возможностям Сущности и типам Компонентов слота, их правилам проверки и целевому типу связи. Явное ограничение типа Сущности может дополнительно сузить совместимость. Встроенные codenames маркетинговой страницы задают стандартные seed-источники; совместимому источнику не нужна дополнительная запись в центральном списке Marketing codenames.

В текущих размещениях Marketing Page каждый обязательный слот выбирает ровно одну цель-источник. Селектор определяет число разрешаемых записей из этого источника: семантический ключ выбирает одну запись, а набор записей или связей — упорядоченный набор. Реестр задаёт <code>maxResolvedRecords</code>, а общий предел resolver дополнительно ограничивает результат. Зарегистрированные Компоненты сортировки и видимости применяются до лимита; настройка <code>maxItems</code> размещения может только уменьшить результат. Метаданные привязок, где порядок не имеет значения, канонизируются для стабильных хешей без изменения порядка записей Сущностей.

## Контракт слотов Marketing Page

Перед публикацией, импортом, восстановлением, активацией или синхронизацией снимка Marketing проверяются значения выбранных записей по зарегистрированному контракту Компонентов и оболочка привязки. Валидатор проверяет обязательные значения, типы данных, ограничения длины и шаблоны, английский и русский тексты локализованных Компонентов, безопасные форматы медиа и действий, а также каждую REF-связь дочерней записи. Некорректные записи блокируются до попадания в опубликованный runtime.

Встроенный шаблон создаёт 14 размещений. У одиннадцати есть привязки Сущностей; аутентификация, язык и цветовая схема являются возможностями хоста без редакционного источника данных.

| Размещение                                                    | Слоты привязок                                                                                                                                                  | Добавление и дублирование в Метахабе                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| <code>marketing.brand</code>                                  | <code>site</code>: семантическая запись <code>MarketingPageSiteSettings</code>                                                                                  | Единичное размещение seed                                             |
| <code>marketing.navigation</code>                             | <code>items</code>: упорядоченный <code>record-set</code>                                                                                                       | Выбор совместимого источника; дубликат повторно использует привязку   |
| <code>marketing.auth</code>                                   | Нет; задаётся хостом                                                                                                                                            | Единичное размещение                                                  |
| <code>languageSwitcher</code>, <code>colorModeSwitcher</code> | Нет; задаются хостом                                                                                                                                            | Существующее поведение общих виджетов                                 |
| <code>marketing.hero</code>                                   | <code>content</code>: семантическая запись                                                                                                                      | Создать или выбрать запись; дубликат копирует привязанную запись      |

REF-компонент преимуществ тарифа (<code>TierRef</code>) указывает на авторитетный идентификатор записи тарифа. Runtime разрешает связь по идентификаторам записей; семантический ключ тарифа не является второй идентичностью связи.

## Авторинг, права и жизненный цикл

Поведение добавления, изменения, дублирования и перепривязки в Метахабе задаётся возможностями реестра. Для семантических слотов используется человекочитаемый список записей; где разрешено, можно создать или изменить запись. Для <code>record-set</code> выбирается источник-Сущность, а записи, их порядок и видимость управляются обычным интерфейсом записей Сущности. Слот <code>relation-set</code> объявляет родительский слот и использует обычный REF-контракт при редактировании дочерних записей. При смене источника родителя нужно сохранить совместимость дочерней связи до сохранения.

После выбора совместимого источника автор может создать для слота отдельную пустую модель источника. Сервер создаёт обычный Объект в Hub маркетинговой страницы и через существующие сервисы Сущностей копирует только зарегистрированную схему Компонентов и их параметры представления. Записи не копируются. Для слота-связи новый REF-компонент указывает на выбранный родительский Объект. Записи затем создаются обычным редактором записей Сущности.

Дублирование Hero и Image копирует выбранную запись Сущности и создаёт привязанное к ней размещение в одной серверной транзакции. Копия проходит обычную проверку записей и правил уникальности ключей; если размещение создать не удалось, копия записи также откатывается. Дублирование Collection, Navigation, Pricing и Footer повторно использует привязки источников и не копирует их записи. Единичные возможности нельзя дублировать. Удаление размещения виджета не удаляет его записи Сущностей. Политики записей из реестра и проверки целостности Сущностей защищают обязательные поля, семантические ключи, активные привязки и цели связей.

Права управления макетами и контентом Метахаба проверяются интерфейсом и повторно сервером. Видимость кнопки не заменяет авторизацию. При записи привязки сервер проверяет весь набор зарегистрированных слотов, разрешает совместимые активные метаданные Сущностей под блокировкой графа макета и проверяет ожидаемую версию макета.

Плейсменты Marketing Page с источником в приложении доступны только для настройки представления: Application-запросы не могут добавлять или дублировать обязательные привязанные размещения, менять их данные Сущностей или заменять привязку. Редактор скрывает Add и Duplicate для таких исходных размещений. Если представление изменено и доступен baseline источника, редактор показывает Reset to source. Размещения и контент меняются в Метахабе, затем публикуются и синхронизируются с уже связанным приложением.

Публикация, снимки, восстановление и синхронизация приложения сохраняют оболочку привязки размещения. Состояние источника приложения хранит доверенную конфигурацию и полный baseline редактируемого представления, активности, порядка, зоны и логического размещения. Синхронизация сравнивает эти семантические поля, а Reset восстанавливает текущий baseline источника с сохранением унаследованной привязки.

Scoped-оверлеи Marketing наследуют идентичность привязки от разрешённого базового плейсмента. В строках оверлеев и импортируемых снимках допускаются только разрешённые изменения представления и размещения; оболочка привязки отклоняется на границах записи и передачи оверлея, а материализация и учёт ссылок используют базовый плейсмент как единственный источник истины.

Удалённый исходный макет с виджетом, связанным с Сущностью, нельзя копировать во владение приложения. Diff помечает такое копирование недоступным, а слой сохранения повторно проверяет это правило до первой записи. При выборе <code>keep_local</code> сохраняется lineage источника, удалённый макет деактивируется, а зависимые виджеты атомарно помещаются в tombstone; последующая безопасная синхронизация может восстановить их. Явный выбор <code>skip_source</code> сохраняет текущее состояние приложения.

## Граница runtime DTO

Авторизованный и публичный runtime Marketing используют одинаковую проверку реестра, селекторов, связей, сортировки, видимости, проекций и жёстких лимитов. Для них подключаются разные разрешённые загрузчики persistence: авторизованный путь использует текущую область приложения/workspace, а публичный читает только опубликованные данные, доступные публичному runtime.

Resolver передаёт Marketing-адаптерам типизированные семантические записи. Итоговый DTO проверяется строгими схемами. Публичный DTO содержит только разрешённый контент и безопасные проекции медиа; в нём нет физических идентификаторов Сущностей и Компонентов, оболочки привязок, метаданных таблиц или произвольных данных строки. Публичный ResourceSource должен разрешиться в допустимый URL. Некорректная привязка, отсутствующий обязательный источник, неверная связь или повреждённый DTO приводят к отказу.

Публичный DTO Marketing обязательно содержит <code>headerPosition</code> и <code>headerWidgets</code>. Строгий запрос копирования макета использует поле <code>entityBindingCopyMode</code>. Это согласованный контракт чистого перехода: сервер и поставляемые клиенты нужно развёртывать вместе; прежние формы payload и запроса не поддерживаются, совместимого fallback нет.

Авторизованный Marketing runtime сериализует только версию эффективного макета и хэш контента, необходимые клиенту, чтобы заметить изменение макета и запросить обновлённые данные. Физические ID макетов, ID и хэши lineage источника остаются внутри runtime-запроса.

<code>@universo-react/apps-template-mui</code> получает типизированную модель <code>data.records</code> и отображает её без импорта persistence и запросов к таблицам Сущностей. Renderer принимает только этот Entity-backed контракт, а поля <code>source</code> и <code>copySource</code> в его DTO отсутствуют.

## Размещения Dashboard и владение данными

Dashboard использует тот же общий контракт реестра пакетов и сохраняет оболочку и адаптивную раскладку MUI 9. Реестр определяет допустимые типы виджетов для каждой зоны, политику источника и копирования, разрешённые настройки представления и возможность содержать другие размещения. Запись размещения хранит только идентификатор экземпляра, зону, порядок, активность, необязательные родителя и слот, конфигурацию представления и нейтральные привязки к источникам. Виджеты с содержимым читают обычные записи Сущностей или ограниченные серверные источники; host-контролы получают сведения о рабочем пространстве, маршруте, пользователе, языке и теме от runtime. Ссылки меню опубликованного Dashboard передают навигацию хосту приложения, чтобы адрес браузера совпадал с загруженным runtime-маршрутом; изолированный standalone-runtime также поддерживает маршруты по пути и hash-формат <code>#/a/...</code>. На маршрутах управления рабочими пространствами в левой, верхней и правой зонах остаются только системные host-размещения из реестра; контентные виджеты и подвал Dashboard скрываются.

| Данные                                                                  | Владелец                                                                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Редакционные заголовки, сообщения, пункты меню, ресурсы и бизнес-записи | Типы Сущностей и их записи, обычно Объекты с Компонентами                 |
| Выбор источника и связи между слотами источников                        | Проверенные привязки макета                                               |
| Внешний вид виджета                                                     | Строгая конфигурация представления из реестра                             |
| Зона, порядок, активность, родитель и слот                              | Отдельная запись размещения макета                                        |
| Прогресс рабочего пространства и пользовательские runtime-значения      | Рабочее пространство или функция runtime, владеющая этим жизненным циклом |
| Состояние выполнения PlayCanvas, Quiz и Interpretation Network          | Их специализированные типизированные runtime-контракты                    |

Страницы <code>Page</code> хранят проверенное содержимое Editor.js-совместимых блоков <code>blockContent</code> в собственных метаданных. Оболочка Dashboard отображает блоки существующим компонентом <code>PageBlocksView</code> в host-content области перед графом размещений; текст страницы не попадает в конфигурацию виджета и не меняет состав размещений.

У каждого размещения Dashboard есть переносимый <code>instanceKey</code>. Он сохраняется при публикации, восстановлении снимка, синхронизации приложения и Reset; физические UUID v7 остаются деталями хранения. Копирование виджета или поддерева контейнера атомарно создаёт новые записи и новые ключи экземпляров. В конфигурации представления нет второй копии бизнес-контента или вложенного списка дочерних виджетов.

Контейнеры используют отдельные записи размещения для дочерних элементов. В родителе хранятся только описания представления колонок или вкладок; в дочернем размещении хранятся ссылка на родителя и семантический ключ слота. В overlay-макете Метахаба эта ссылка может указывать на унаследованное размещение базового макета. Snapshot- и авторинговые границы проверяют общий эффективный граф, а материализация приложения переносит его в один макет приложения. Ниже приведён схематичный фрагмент только связи дочернего элемента с родителем; это не полная запись размещения и не готовый API-payload:

```json
{
    "widgetKey": "detailsTable",
    "instanceKey": "records-table",
    "parentWidgetId": "<локальный для снимка идентификатор родителя>",
    "slotKey": "column:main"
}
```

UUID родителя в экспортированном снимке действует только внутри снимка и переназначается при восстановлении. Семантический хэш использует ключ экземпляра родителя и слот, а не физические UUID. Серверная проверка графа отклоняет отсутствующих и чужих родителей, самоссылки, циклы, неизвестные слоты, несовместимые типы дочерних виджетов и повторяющиеся ключи экземпляров.

Для размещения под управлением источника Метахаб остаётся владельцем идентичности источника, привязок, зоны и вложенной композиции. Редактор приложения может менять только поля представления и настройки развёртывания, явно разрешённые политикой реестра; Reset восстанавливает текущий baseline источника. Интерфейс показывает эти ограничения, а сервисы записи независимо проверяют их на сервере.

Runtime Dashboard загружает только зарегистрированные источники, проверяет доступ на сервере, применяет фиксированные лимиты и возвращает строгие DTO по allowlist. Авторизованное чтение применяет обычные правила owner/shared к каждой записи источника и к родительским записям relation-set. Анонимный запрос не получает доступ к Объектам с owner/shared-защитой; некорректные метаданные доступа также приводят к отказу. Изолированный renderer пакета приложений не получает имена таблиц, SQL-фрагменты, оболочки привязок или физические идентификаторы Сущностей и Компонентов. Пустые данные, отказ в доступе, отсутствующий источник и ошибка загрузки отображаются как разные локализованные состояния.

Шаблоны Basic, Basic Demo, Empty, 1C-Compatible, LMS, Interpretation Network и PlayCanvas создают этот общий формат размещений. Basic Demo добавляет реальные записи Сущностей и ограниченные источники метрик и рядов; остальные шаблоны включают только нужную оболочку и специализированные runtime-размещения. Этот переход выполняется без совместимого legacy-читателя и без повышения версий схемы или шаблона.

Сгенерированная навигация Dashboard выводит видимые Страницы и группирует их по связанным Хабам. Объекты по умолчанию не попадают в навигацию; шаблон может явно показать выбранный Объект как основную ссылку через `config.runtime.menuVisibility: "primary"`. В формах создания и редактирования Объекта в Метахабе этот параметр и семантическая иконка доступны на вкладке «Навигация»; при копировании сохраняется выбор — скрывать Объект или показывать его. Такой opt-in не позволяет обычным источникам данных и регистрам заполнять боковое меню. Иконки Страниц, Хабов и выбранных Объектов задаются ограниченной семантической метаинформацией и отображаются готовыми иконками MUI; для неизвестных значений используются безопасные значения по умолчанию. Общая runtime-оболочка отображает переключатели языка и темы по одному разу, а подписи меню темы берёт из общего пространства переводов `common`.

Этот переход меняет wire-контракт Dashboard для согласованного релиза платформы. Старые корневые настройки <code>show\*</code>, <code>defaultViewMode</code>, <code>cardColumns</code>, <code>rowHeight</code> и <code>enableRowReordering</code> больше не принимаются: внешний вид задаётся для каждого размещения, а поведение оболочки — через <code>sideMenu</code> и <code>objectBehavior</code>. Автоматического преобразования нет. Строгая проверка также отклоняет вложенные массивы дочерних виджетов и сохранённые, импортированные или синхронизируемые записи размещений без обязательного семантического ключа и явных полей родителя/слота. Сервер создаёт <code>instanceKey</code> каждого размещения. В запросах Application используется <code>parentWidgetId</code> (UUID записи родителя), а при настройке Метахаба — <code>parentInstanceKey</code> (семантический ключ родителя); для корневого размещения родитель и слот опускаются, для дочернего передаются вместе. В ответах есть <code>instanceKey</code>, <code>parentWidgetId</code> и <code>slotKey</code>; у корневого размещения родитель и слот равны null. Развёртывайте согласованные версии backend, фронтендов Метахаба и Приложения и изолированного runtime-пакета шаблона приложений вместе; внешним клиентам REST API необходимо обновить типы запросов и ответов согласно новым контрактам. Создавайте метахабы и приложения Dashboard из актуальных шаблонов и перегенерируйте снимки. Прежние данные Dashboard автоматически не обновляются.

## Локализация

Локализованные Компоненты Сущностей остаются источником контента. Политика слота задаёт обязательные локали; проверка снимка Marketing требует английский и русский текст для локализованных полей. В интерфейсе выбора источников и записей Метахаба, заголовках форм, пустых и загрузочных состояниях, ошибках проверки, отказах по правам и конфликтах используются переводы EN/RU. Каждый зарегистрированный runtime-виджет выбирает локализованные значения по своему типизированному DTO-контракту с разрешённым списком полей, используя общие правила выбора локали.
